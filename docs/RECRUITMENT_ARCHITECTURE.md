# 채용 관리 모듈 설계

## 범위

기존 AIroom의 Express, 관리자 세션, Redis, 정적 HTML 구조를 유지한다. 새 프레임워크나 별도 호스팅은 도입하지 않는다. `/recruitment`는 별도 작업 화면이고 메인 두 HTML에 채용 관리 메뉴를 추가한다. 원본 Google 파일은 수정하지 않는다.

```text
public/recruitment/ (설정 · 평가 · 통계 · HTML/PDF 출력 UI)
  → /api/recruitments (권한·입력 검증)
    → domain.js (순수 상태 전이와 집계)
    → store.js (Redis CAS / 로컬 원자적 파일 교체)
    → providers/mock.js (웹 평가 공간 시작 전이)
    → providers/google.js (Drive 연결 경계 · 결과 문서 보관용)
    → exports.js (확정 스냅샷 → HTML / XLSX / ZIP)
    → google-auth.js (OAuth · 암호화 토큰 · 계정 확인)
```

## 상태와 불변 조건

| 상태 | 가능한 작업 | 다음 단계 조건 |
|---|---|---|
| draft | 설정 확인, 위원 초대, 평가 시작 | 설정 검증 완료 |
| document | 서류 점수 임시 저장·제출·재개방 | 모든 서류위원 제출, 참석 상태 일치, 대상자·선정 근거 입력 |
| interview | 면접 점수 임시 저장·제출·재개방 | 모든 면접위원 제출, 참석 상태 일치 |
| finalized | 통계 확인, HTML/XLSX/ZIP 다운로드 | 불변 스냅샷, 점수 재개방 금지 |

최대 지원자 20명, 평가위원 5명(전형별 1~5명), 면접대상자 4명. 이름 대신 UUID와 접수번호를 사용한다. 생성 이후 설정 변경·확정본 정정 버전·서류 단계 되돌리기는 후속 범위이며 현재 API는 허용하지 않는다.

## 집계 규칙

- 원본 서류 항목: 학력6 + 자격증6 + 경력6 + 지속근무6 + 자기소개서26 = 50. 기본 UI는 세부 자격증 종류를 합친 항목 점수를 받으며 총 최대6점을 검증한다. 원본 심사표의 학력 선택형·자격증별 세부 행 입력은 후속 웹 UI 확장 대상이다.
- 면접: 인성10 + 교직관10 + 소양10 + 수업이해10 + 학생이해10 = 50.
- 가점은 생성 시 선택. 사용 시 0/2.5/5, 기본점수20 이상, 확인 근거 필수. 이는 원본 심사표를 반영한 개발 규칙이며 기관이 적용할 실제 기준을 확정해야 한다.
- 점수 입력은 0.5점 단위. 빈칸은 미입력이고 0점과 다르다.
- 평균은 배정 위원 전원 제출 후, 전형별 소수 첫째 자리로 반올림. 최종 합산은 표시된 평균끼리 더한다. 순위는 설정된 합산 또는 면접 평균 기준으로 계산한다.
- 모든 위원이 불참 표시하면 해당 전형의 점수·순위 제외. 참석 표시에 불일치가 있으면 확정을 거부한다.
- 동점은 경쟁 순위(1,2,2,4). UI 표시 순서가 접수번호순이어도 동점 우선 선발을 의미하지 않는다. 자동 합격 결정 없음.
- 서류 대상자 확정은 관리자 선택 + 근거 필수. 상위순위 자동 강제는 하지 않는다.

## 인증·권한

- 관리: AIroom 기존 `validateSession` 세션 중 role 이 `admin` 또는 `user` 면 채용 관리자로 인정한다.
  채용 탭이 백암이 안에 있어 접근 코드를 두 번 묻지 않기 위한 결정이다. 따라서 **백암이 접근 코드를 아는
  사람은 누구나 지원자 명단과 평가 점수를 열람·수정할 수 있다.** 실제 지원자 정보를 넣기 전에 이 범위가
  기관 기준에 맞는지 확인해야 한다. 좁히려면 `routes.js` 의 `MANAGER_ROLES` 를 `['admin']` 으로 되돌린다.
- 평가: 위원별 256비트 임의 토큰. 서버에는 SHA-256 해시만 저장, 7일 만료. 재발급하면 이전 토큰 무효화.
- 초대 토큰은 URL fragment로 전달하고 즉시 주소에서 제거한다. 브라우저 sessionStorage에만 저장, 서버 요청은 헤더로 전송한다. 자동 이메일 발송 없음.
- 역할이나 reviewerId를 클라이언트가 임의 지정해서 점수를 쓰지 못한다. 서버가 초대 토큰의 위원에 바인딩한다.
- 공동 열람 모델: 배정된 위원은 같은 채용 전체 평가를 볼 수 있지만 본인 평가만 입력 가능. 타 채용에는 접근 불가. 다른 위원 점수 비공개가 필요하면 응답 projection 및 Google 파일 분리가 필요하다.
- 전체 출력물 다운로드, 초대, 재개방, 면접대상자·최종 확정은 관리자 전용.
- 공유 링크는 실제 인물 신원 검증을 대신하지 않는다. 운영 단계의 Google 로그인 연동 전까지 링크를 위원에게만 전달해야 한다.

## 데이터 저장과 동시 편집

채용 한 건을 버전이 있는 JSON aggregate로 저장한다. 지원자/위원/규칙/평가/스냅샷/이력을 포함한다. 최대 크기가 작은 학교 채용용이다.

- 로컬: `data/recruitment/{uuid}.json`, 쓰기 큐 → 임시 파일 → rename. 단일 프로세스용.
- Redis: `recruitment:{id}` 및 `recruitment:index`. Lua로 버전 비교와 저장을 한 번에 수행한다.
- 모든 변경은 version 필수. 오래된 화면에서 저장하면 HTTP409, 기존 입력을 덮어쓰지 않는다. 사용자가 최신 상태 확인 후 재입력한다.
- 저장 오류를 성공으로 처리하지 않는다. 서버리스에서 Redis 장애 시 로컬 임시 파일로 우회하지 않는다.
- 평가 시작과 확정 재호출은 중복 전이·확정본을 만들지 않는다.
- 설정·배정·상태·점수의 기준은 전부 DB다. 평가는 웹에서 이루어지므로 외부 시스템과 점수를 주고받지 않는다. Drive 업로드를 붙일 때도 업로드 대상은 확정 스냅샷에서 만든 결과 문서뿐이며, 점수의 기준이 Drive로 옮겨가지 않는다.

## API 계약

모든 변경 요청(JSON)은 `version`을 포함한다(생성 제외). 관리자 `X-Auth-Token`, 위원 `X-Recruitment-Token`. 응답에는 개인 초대 토큰 해시를 포함하지 않는다.

| 메서드 | /api/recruitments 이후 경로 | 역할 |
|---|---|---|
| GET/POST | / | 관리자 목록/생성 |
| GET | /config | 연결 상태·폴더 설정 |
| GET | /:id | 관리자/배정 위원 조회 |
| POST | /:id/provision | 관리자 평가 시작(웹 평가 공간 개시) |
| POST | /:id/invites/:reviewerId | 위원 링크 발급·회전 |
| POST | /:id/evaluations/:stage/save | 본인 평가 임시 저장 |
| POST | /:id/evaluations/:stage/submit | 본인 평가 검증·제출 |
| POST | /:id/evaluations/:stage/reopen | 관리자 현재 전형 재개방 |
| POST | /:id/shortlist | 관리자 대상자 확정 |
| POST | /:id/finalize | 관리자 확정 스냅샷 |
| GET | /:id/export/html 또는 xlsx 또는 zip | 관리자 다운로드 |
| POST | /google/start | 관리자 OAuth URL 발급 |
| GET | /google/callback | state 검증 후 토큰 암호화 저장 |
| POST | /google/check | 운영 계정·폴더 권한 검사 (읽기만) |

## Google Drive 연동 범위와 남은 작업

평가는 전부 이 웹에서 한다. Google 스프레드시트 템플릿을 복사해 위원이 시트에서 채점하던 설계는 폐기했다.
따라서 시트 복사·수식 정비·탭/셀 매핑·보호 범위 같은 작업은 더 이상 이 모듈의 범위가 아니다.

Drive 는 **확정 결과 문서 보관** 용도로만 남긴다. `providers/google.js`에는 운영 계정·폴더 권한 확인
(`checkConnection`), 폴더 생성(`createFolder`), 파일 공유(`shareWithReviewer`)와 Drive 전용 `request`만 있다.
Sheets API 클라이언트와 템플릿 매핑 코드는 제거했다.

1. 확정본에서 만든 HTML·Excel·ZIP 을 채용별 하위 폴더에 업로드하고, 반환된 실제 webViewLink 를 DB에 저장한다. 업로드하지 않은 파일의 링크를 Google URL처럼 표시하지 않는다.
2. DB 채용ID를 Drive `appProperties`에 기록하고 폴더 생성·업로드 단계별 완료 ID를 저장한다. 재시도 전 조회하여 중복 업로드를 막는다.
3. 업로드는 확정(finalize) 이후에만 수행한다. 진행 중 점수는 Drive 에 올리지 않는다.
4. 상위 폴더의 공개·도메인 공유가 남아 있으면 업로드를 시작하지 않는다(`checkConnection` 409).
5. Google 의 파일 단위 권한은 공유 파일 전체 열람을 허용한다. 보관 폴더를 위원 전체에게 공유하지 말고 필요한 관리자에게만 공유한다.

## HTML → PDF와 Excel

- HTML은 확정 스냅샷만 사용하며 모든 사용자 문자열을 escape한다. 외부 폰트·이미지·라이브 데이터 요청 없음.
- A4 가로 인쇄 CSS, 문서별 페이지 구분, 5명 단위 위원 채점표, 서약서, 서류 집계표, 최종 집계표.
- PDF는 브라우저 인쇄 대화상자에서 저장한다. 서버가 PDF 바이너리를 직접 생성하는 기능은 없다.
- 서약서는 원본 핵심을 반영한 기관 검토용 문구이며 기관 확정 문구로 교체 가능.
- 위원은 초대 링크로 접속해 캔버스에 직접 서명한다. 서명은 PNG 바이트로 디코딩·재인코딩해 저장하므로
  원본 data URI 에 섞인 다른 페이로드는 버려진다. 60KB 상한, PNG 매직 검사.
- 서명 없이는 평가를 제출할 수 없다. 서약서 페이지와 위원별 채점표에 서명 이미지와 서명 시각이 인쇄되고,
  Excel 에 '평가위원 및 서약' 시트가 추가된다.
- 위원에게는 남의 서명 이미지를 내려보내지 않는다(서명 여부와 시각만). 관리자는 전체를 본다.
- 전자서명이 기관이 요구하는 자필 서명을 대체하는지는 기관이 판단할 사항이다.
- Excel은 설정/규칙, 서류 집계, 면접 최종 집계, 위원별 상세의 4개 시트. 확정 결과값을 저장하며 live 수식 재계산에 의존하지 않는다. 문자열은 ExcelJS 문자열 셀로 쓰고 수식으로 실행하지 않는다.
- ZIP은 HTML/XLSX/확정 JSON/안내문. 현재는 기기 다운로드만 제공한다. Drive 보관 업로드는 위 절의 남은 작업이다.

## 실행과 검증

```powershell
npm ci
npm run test:recruitment
$env:PORT=3100
npm start
```

http://localhost:3100/recruitment → 관리자 로그인 → 새 채용 → 예시 채우기 → 생성 → 평가 시작 → 위원별 초대 링크 → 서류 제출 → 관리자 대상자 확정 → 면접 제출 → 결과 확정 → HTML/PDF 및 Excel 다운로드.

예시는 사용자가 명시적으로 채우기를 눌렀을 때만 들어간다. 실데이터를 기본값으로 넣지 않는다. 기존 AIroom 운영 인증 설정은 이 모듈에서 변경하지 않는다.
