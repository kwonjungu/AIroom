# AIroom 초등 바이브코딩 상용화 재설계 계획

작성일: 2026-09-26 · 상태: 구현 착수용 설계안 · 이번 산출물은 계획서이며 제품 구현 완료 보고가 아니다.

**저학년은 카드로 생각을 조립하고, 3~6학년은 말과 블록으로 실제 플레이 가능한 게임을 만들고 고치는 앱으로 재설계한다.** 태블릿·노트북·크롬북을 주 기기로 삼는다. 기존 캐릭터·학습 콘텐츠·DSL·블록을 자산으로 유지하면서 화면, 상태 관리, 실행기, AI 생성 절차를 모듈 단위로 교체한다.

## 문서 사용 순서

1. 이 문서: 제품 목표, 학년별 UX, 반응형 규격, 모드별 개선, 출시 순서.
2. [AI·게임·에셋 하네스 및 계약](./HARNESS-AND-CONTRACTS.md): 생성·수정·검증·저장·복구의 구현 명세.
3. [Claude 병렬 구현 작업 지시서](./PARALLEL-IMPLEMENTATION.md): 파일 소유권, 선행 작업, 작업 패킷, 통합 절차.
4. [검수·평가·출시 기준](./ACCEPTANCE-AND-EVALS.md): 자동 검사, 실제 기기 검증, 모델 비교, 출시 차단 조건.
5. [현행 브라우저 측정](./evidence/browser-audit.json): 배포 화면의 관측값. `evidence/*.png`는 개편 전 화면이다.

사용자가 지칭한 “Claude OPUS 5.5”는 **후속 구현 작업자의 명칭**으로 사용한다. 이 문서는 해당 모델의 공개 여부·API ID·비용을 가정하지 않는다. 사용 가능한 Claude 환경에서 작업 패킷을 배정하면 된다. 학생용 앱의 Groq 런타임과 개발용 Claude 작업자는 별개다.

## 1. 확정 요구와 설계 원칙

| 항목 | 확정 내용 |
|---|---|
| 저학년 | 카드 코딩: 별까지 가기, 도형 겹치기. 읽기·타이핑 부담을 최소화 |
| 3~6학년 | 거북이, 픽셀, 미로, 게임 공방. 블록과 자연어를 함께 사용 |
| 우선 기기 | 태블릿, 노트북, 크롬북. 터치·마우스·키보드 동등 지원 |
| 우선 개선 | 게임 제작 성공률, 작은 단계 UI, 도형 겹치기, 화면 상세 품질 |
| AI | Groq 기반. 모델을 바꾸는 것만으로 품질 문제가 해결된다고 가정하지 않음 |
| 이미지·소리 | 공급자 API로 자동 생성 가능하게 설계. 키·공급자·예산은 서버 설정 |
| 개발 방식 | 여러 Claude 작업자가 독립 모듈을 병렬 구현한 뒤 계약 테스트로 통합 |

첫 화면은 `그림 카드로 시작`과 `말과 블록으로 만들기`의 두 경로로 정리한다. 학년은 기본 경로를 추천하는 정보이며 능력을 고정하는 잠금 장치가 아니다. 교사는 반별 시작 모드를 지정하고 학생은 허용된 모드 안에서 탐색한다.

완성의 기준은 예쁜 스크린샷이 아니라 **아이 혼자 시작하고, 실행하고, 바꾸고, 저장하고, 다시 열 수 있는 것**이다. 생성이 실패해도 이전 작품은 유지되고, 인터넷이 느려도 준비된 게임과 카드 활동은 계속할 수 있어야 한다.

## 2. 현행 구조 및 확인한 문제

### 2.1 감사 범위와 한계

- 배포: https://a-iroom.vercel.app/vibecoding.html — HTTP 200 및 Chromium 화면 확인.
- 저장소: https://github.com/kwonjungu/AIroom
- 로컬 기준: `claude/school-admin-portal-APgza`, HEAD `76b53b90c6656a0ba335afdc0e5d17b7f85270d5`.
- 로컬 `public/vibecoding.html`: 6,078줄, 407,409바이트. 사용자 미커밋 수정 1건이 있었다. `_wireDropZone()` 리스너 중복 등록 방지 수정이며 보존해야 한다.
- 당시 배포 HTML: 400,817바이트. 로컬과 SHA-256이 다르다. **로컬 소스 분석과 배포 화면 관측을 구분**하고, 착수 시 실제 production 커밋을 다시 확인한다.
- 브라우저 감사는 학생 정보 조회·API 쓰기를 차단하고 UI 모드를 프로그램적으로 선택했다. 실계정·유료 생성·서버 권한 침투 검사는 수행하지 않았다.
- 1440×900, 768×1024, 보조 화면 390×844를 관측했다. 실제 iPad·Android·ChromeOS 및 1366×768 검수는 후속 출시 게이트다. 현재 관측을 전체 기기 통과로 해석하지 않는다.
- `CLAUDE.md`에는 6개 회귀 테스트가 적혀 있지만 이 로컬 체크아웃 `_check/`에는 `rate-limit-test.js`만 있다. 기존 테스트가 존재·통과한다고 간주하지 않는다.

## 3. 학년별 경험 재구성

| 구분 | 저학년 카드 코딩 | 3~4학년 | 5~6학년 |
|---|---|---|---|
| 시작 | 그림 2~3개 선택, 바로 시도 | 하고 싶은 것 선택 + 짧은 문장 | 장르·규칙·조건 직접 설명 |
| 편집 | 그림 카드, 눌러 추가, 순서 바꾸기 | 자연어 + 핵심 블록 | 자연어 + 변수·조건·이벤트 블록 |
| 설명 | 한 번에 한 문장, 선택형 읽어주기 | 짧은 이유와 변경 강조 | 규칙·변수 흐름 및 테스트 결과 |
| 실수 피드백 | 다음 한 행동을 그림으로 | 어느 블록을 바꿀지 안내 | 실패 조건과 최소 수정 제안 |
| 목표 | 순서·반복·위치·겹침 이해 | 움직임·충돌·점수 게임 완성 | 난이도·상태·변수를 수정하며 검증 |
| 평가 | 시도와 설명을 격려 | 실행 → 수정 → 재실행 | 의도와 실제 규칙 일치, 수정의 영향 설명 |

학년은 UI 프리셋이다. 같은 개념의 쉬운/기본/확장 과제를 제공한다. 초반부터 여섯 개 모드를 모두 동등하게 노출하지 않는다.

40분 수업 예시: 0~5분 예시 게임 플레이·목표 선택, 5~12분 첫 작품, 12~25분 두 번 이상 수정·실행, 25~33분 짝과 테스트, 33~40분 저장·바뀐 규칙 한 줄 설명. 시간은 수업 구성 제안이며 실제 사용자 조사로 조정한다.

## 4. 화면 정보 구조

### 4.1 시작 화면

- 주 CTA: `이어서 만들기`, 보조 CTA: `새로 만들기`. 첫 방문에는 학습 경로 두 개와 대표 그림만 제공.
- 학급 코드는 교사가 배포. 연습은 식별 없이 가능. 저장·학급 공유 시 세션을 발급한다.
- 학교 검색·학년·반·번호를 채우는 절차가 첫 놀이보다 앞서지 않게 한다.
- 내 작품은 썸네일·제목·마지막 저장 상태·계속하기. 실패 작업은 `마지막으로 잘 된 작품 열기`.
- 교사 기능은 별도 진입점과 서버 권한으로 분리한다. 학생 화면에서 개발 오류·키 설정·모델명이 기본 노출되지 않게 한다.

### 4.2 단계 선택: 지도와 작업 단계 분리

**학습 지도:** 챕터 제목, 완료 수, 현재 미션, 4~6개 미션 카드. 긴 가로 트랙 전체를 축소하지 않는다. 챕터 이동은 이전/다음 또는 목록, 스크롤 위치 복원. 배경 길과 캐릭터는 장식이며 버튼·제목을 가리지 않는다.

**작업 단계:** `① 생각하기 → ② 만들기 → ③ 해보기 → ④ 바꾸기 → ⑤ 저장하기`. 현재 단계에 큰 제목과 다음 행동을 표시한다. AI 처리 상태의 `준비·조립·검사`와 구분한다. 기존 작품 편집 시 단계를 되돌아갈 수 있다.

| 요소 | 목표 규격 |
|---|---|
| 단계 카드 | 저학년 최소 112×128px, 기본 104×120px. 확대/언어 길이에 따라 높이 증가 |
| 단계 아이콘 | 저학년 80~96px, 3~6학년 64~80px |
| 단계 제목 | 저학년 20px, 기본 18px. 2줄까지 자연스럽게 배치 |
| 현재 단계 | 번호 + `지금 여기` + 테두리. 색만으로 표시하지 않음 |
| 잠금 | 자물쇠 + 이유. 포커스 가능 설명, 교사가 풀 수 있는 학습 잠금 |
| 완료 | 체크 + 결과. 별은 보조이고 재시도 횟수로 창의적 실험을 감점하지 않음 |
| 공방 템플릿 | 시작 화면에서 240px 이상 카드 폭, 실제 게임 그림과 조작 방법 표시 |

### 4.3 저학년 작업 화면

상단은 돌아가기·미션 제목·현재 단계, 중앙은 `만들 그림 / 내가 만든 그림`, 하단은 카드 순서·팔레트·실행 버튼. 캐릭터는 안내를 할 때만 작은 영역에 등장한다. 캐릭터와 꾸밈 배경이 작업 공간을 밀어내지 않는다.

- `누르면 추가`가 기본이며 드래그는 추가 선택지다. 카드 이동은 잡아 끌기 외에 `앞으로/뒤로` 버튼과 키보드 지원.
- 카드 1~6장: 한 줄. 많아지면 줄바꿈 또는 페이지 이동. 마지막 카드가 가려져도 전체 카드 수 표시.
- 카드 선택 시 테두리·번호·이름을 함께 강조. 현재 실행 카드와 캔버스 결과를 같은 번호로 연결.
- 실행 속도 `천천히 / 보통`, 일시정지, 한 단계씩, 되돌리기, 다시하기.
- 잘못 놓았을 때 곧바로 큰 실패 모달을 띄우지 않는다. 해당 카드 아래 한 가지 수정 힌트.
- 전체 비우기는 되돌릴 수 있는 동작. 저장한 원본 삭제는 별도 확인.

### 4.4 3~6학년 작업 화면

무대와 편집을 주 영역으로, AI는 작업 중 필요한 만큼 펼친다. `만들기 / 해보기` 전환 시 조작판이 편집기를 덮지 않는다. AI 적용 전에는 `바뀔 것: 속도 3→5, 목숨 3 유지`를 보여주고 한 번에 되돌릴 수 있게 한다.

한글 입력은 IME 조합 중 Enter 전송을 막는다. 생성 중에도 초안 입력·취소·기존 게임 플레이 가능. 예시 칩은 `빨리 해줘`보다 `사과가 조금 더 천천히 떨어지게`처럼 현재 작품에 연결한다. 코드는 기본 접힘, 학습자는 블록으로 수정할 수 있다.

## 5. 반응형·시각 디자인 시스템

화면 크기에 따른 기본 배치를 정하되 패널의 실제 가용 폭을 함께 판단한다. 태블릿 가로 1024px에서 데스크톱 3열을 강제하지 않는다. hover가 없는 기기에서 모든 기능에 접근 가능해야 한다.

| 환경 | 기본 배치 | 필수 상세 |
|---|---|---|
| 1280px 이상, 충분한 높이 | 무대 5 : 편집 4 : 접을 수 있는 도움 3 | 각 패널 최소 폭 충족 시만 3열 |
| 1024~1279px / 크롬북 1366×768 | 무대 + 편집 2열, AI는 편집 영역 탭 | 상단 2줄 이하, 실행 버튼 고정, 화면 높이 고려 |
| 768~1023px 태블릿 세로 | 무대·목표 위, 편집 아래 | 내부 스크롤 1개 중심. AI 입력 시 무대 축약 가능 |
| 태블릿 가로 | 2열 + 56px 터치 조작판 | 가상 키보드가 열리면 입력·전송·취소가 계속 보임 |
| 768px 미만 보조 대응 | 한 작업 탭씩 + 무대 펼치기 | 휴대폰용 전용 제품 범위는 후순위, 작업 유실 금지 |

`100dvh`만으로 키보드 문제를 해결했다고 판단하지 않는다. `VisualViewport` 또는 동등한 가시영역 처리를 실제 Safari/Chrome 키보드로 검증한다. 작은 높이에서는 문서 세로 스크롤을 허용한다. 본문 가로 넘침 0, 의도된 블록 캔버스는 별도 패닝.

| 토큰 | 기본 | 저학년 |
|---|---|---|
| 본문 | 18px / 줄높이 1.55 | 20px / 1.6 |
| 보조 설명 | 16px | 18px |
| 중요 버튼 | 높이 48~56px | 높이 56~64px |
| 색·위치·닫기 조작 | 최소 48×48px | 최소 56×56px |
| 버튼 간격 | 8px 이상 | 12px 이상 |
| 간격 단위 | 4, 8, 12, 16, 24, 32px | 동일, 더 큰 간격 우선 |
| 포커스 | 3px 외곽선 + 충분한 명도 차 | 동일 |

18/20px 본문과 48/56px 조작 크기는 **이 제품의 목표**다. WCAG의 모든 기준이 이 수치를 요구하는 것은 아니다. W3C의 강화된 타깃 기준은 44 CSS px이며, 본 제품은 아동의 터치를 위해 더 크게 잡는다. [W3C 근거](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)

기본 팔레트는 밝은 중립 배경·진한 본문·모드별 강조색 한 개다. 오렌지/흰색 같은 조합은 실제 대비를 측정해 보정한다. 주요 화면은 색 4~5개 이내, 폰트는 읽기용과 제목용 두 종류 이내. 버튼 글자를 이미지 안에 넣지 않는다. `prefers-reduced-motion`에서 튀기기·색종이·화면 이동을 줄인다. 성공 효과 0.6~1.2초, 상시 흔들림 제거, 소리 기본 설정과 수업용 일괄 음소거 제공.

## 6. 도형 겹치기 전면 개선

### 6.1 학습을 순서와 앞뒤 관계로 명확히 하기

“뒤에 놓인 카드가 그림에서는 위를 덮는다”를 첫 미션에서 직접 보여준다. 미션 예시는 집(네모→세모), 눈사람(큰 원→작은 원), 나무(기둥→잎), 로켓, 물고기. 처음 3개는 도형 수와 색 고정, 다음은 순서 변경, 이후 위치·색·크기 중 한 요소씩 추가한다.

기존 12개 미션은 삭제하지 말고 새 규격으로 재검수한다. 모든 미션에 목표 개념, 허용 도형, 정답 조건, 동등 정답, 오답 피드백, 배경 없는 목표 마스크를 둔다.

### 6.2 편집 인터랙션

- 목표와 내 그림을 기본 200~280px 이상으로 비교하되 실제 공간에 맞춰 축소한다. 목표를 누르면 큰 비교 보기. 작은 목표만 상단 모서리에 두지 않는다.
- `나란히 / 겹쳐 보기 / 다른 부분`을 제공. 겹쳐 보기는 35% 고스트, 차이 보기는 색 + 무늬로 표시.
- `앞으로`는 카드 순서인지 그림 레이어인지 불명확하다. `먼저 찍기 / 나중에 찍기`로 표기하고 캔버스에서 바뀔 모습을 미리 보여준다.
- 위치 선택은 이름 있는 3×3 칸: `왼쪽 위`, `가운데` 등. 저학년 56px 칸, 포인터 선택과 버튼 모두 지원.
- 색에는 이름·선택 체크, 흰색에도 경계 표시. 크기 `작게/중간/크게`를 실제 크기 그림으로 보여준다.
- 선택한 카드만 속성 패널을 열고 다중 속성을 한꺼번에 바꾼 뒤 `완료`. 매 탭마다 팝업을 닫지 않는다.
- 좌표는 논리 좌표, 화면·DPR 변환은 렌더러 한 곳에서 처리. 드래그 시작 시 `setPointerCapture`, `pointercancel` 복구, 선택 핸들에만 `touch-action:none` 적용.

### 6.3 공정한 채점

빈 화면과 장식 배경을 정답 점수에 넣지 않는다. 배경을 제외한 목표/학생 전경 마스크의 합집합을 분모로 삼고, 색 일치·도형 속성·학습상 중요한 앞뒤 관계를 따로 계산한다. 완전히 가려진 도형과 교환해도 결과가 같은 비겹침 도형을 구분한다. 목표 픽셀 비교 하나로 모든 정답을 결정하지 않는다.

P0 목표: 빈 작품 0%; 정확한 목표 100%; 필수 도형 누락·필수 레이어 역전은 완료 불가; 같은 그림과 학습 조건을 만족하는 다른 순서는 허용. 허용 오차와 가중치는 미션 데이터로 버전 관리하고 적합/부적합 예제로 보정한다. 안티앨리어싱 차이로 정답을 탈락시키지 않는다.

학생에게는 `네모는 잘 놓았어. 세모를 나중에 찍어 볼까?`처럼 차이를 설명한다. 상세 퍼센트는 교사/고급 보기로 이동. 실패 횟수에 따른 별 감점 대신 `완성`, `다르게 시도`, `설명해 보기`를 별도 성취로 기록한다.

## 7. 다른 학습 모드의 상세 개선

| 모드 | 유지할 가치 | 구체적 개선 | 완료 증거 |
|---|---|---|---|
| 별까지 가기 | 그림 카드로 순서·반복 익히기 | 이동 예고 화살표, 한 칸 실행, 도착/벽 충돌 설명, 터치 순서 편집 | 키보드 없이 미션 완성, 취소 후 복구 |
| 거북이 | 기하와 회전의 시각화 | 현재 방향·회전각 크게, 목표 고스트 토글, 선을 따라 실행 카드 강조, 화면 밖 선 재맞춤 | 삼각형·사각형·반복 패턴, 확대 후 좌표 일치 |
| 픽셀 | 격자·좌표·반복 | 목표 확대, 큰 좌표 레이블, 손가락 드래그 칠하기, 한 번에 되돌리기, 색 이름 | 터치 이동 중 누락/중복 입력 없음 |
| 미로 | 순차·반복·조건 | 로봇의 기준 방향 표시, 충돌 위치 설명, 실행 속도/일시정지, 경로 미리보기 | 기존 미션 전부 도달 가능, 리셋 결정적 |
| 게임 공방 | 자유 제작, 이벤트와 변수 | 템플릿·프로젝트 저장·패치 수정·실행 검증·큰 플레이 모드 | 생성 후 두 번 수정해도 기존 규칙 유지 |

공통 초기화 인터페이스를 `enter / pause / resume / dispose`로 통일한다. 모드 변경 때 실행·소리·포인터·AI 요청·이벤트 리스너가 정리되는지 검사한다. 아직 실행 가능한 문법과 준비 중인 문법을 UI에서 혼동시키지 않는다.

## 8. 게임 공방의 제품 설계

### 8.1 첫 출시 장르와 범위

첫 출시의 품질 보증 범위는 **받기, 피하기, 모으기, 미로 탈출** 네 장르다. 기존 공방의 사과 받기·운석 피하기·보석 모으기를 먼저 고도화하고 미로 엔진을 네 번째 템플릿으로 연결한다. `나만의 게임`도 이 네 장르의 규칙 조합부터 시작한다. 점프 플랫폼·멀티플레이·3D·임의 JavaScript 프로젝트는 후속 범위다.

| 장르 | 기본 완성 규칙 | 학생이 바꾸는 것 | 자동 검증 |
|---|---|---|---|
| 받기 | 좌우 이동, 떨어지는 물체, 점수, 제한 시간, 재시작 | 캐릭터, 낙하 속도, 목표 점수 | 받기 시 점수 1회 증가, 놓치기 처리 |
| 피하기 | 이동, 장애물 생성, 목숨, 잠깐 무적, 생존 성공 | 장애물 간격, 목숨, 속도 | 연속 접촉 중 목숨 폭주 방지 |
| 모으기 | 이동, 보석 생성, 수집, 목표 달성 | 지도·보석 수·방해 요소 | 수집 제거, 중복 점수 없음 |
| 미로 탈출 | 벽·출발·목표, 충돌, 도착, 재시작 | 길·열쇠·문·제한 조건 | 기본 맵 경로 탐색, 도착 이벤트 |

### 8.2 제작 흐름

1. 예시를 10초 정도 플레이하거나 바로 건너뛴다.
2. `무슨 게임? 누가 나와? 어떻게 이겨?`를 그림·문장으로 선택. 이미 충분히 설명했다면 다시 묻지 않는다.
3. 준비된 엔진에 검증된 규칙을 조립해 즉시 플레이 가능한 초안을 만든다. 이미지 생성은 병렬로 진행하며 게임 시작을 막지 않는다.
4. `해보기`로 이동. 크롬북은 방향키/WASD, 태블릿은 큰 방향판·장르별 드래그. 설명은 첫 조작 전에 짧게.
5. 자연어로 수정. 바뀐 부분과 유지한 규칙을 보여주고, 실행한 뒤 이전 버전과 비교·복구.
6. 제목·썸네일·작품 버전 저장. 공유는 기본 학급 범위, 교사가 켠 범위만 허용.

받기 게임 예: `고양이가 생선을 받아. 10개면 성공` → 검증된 템플릿 생성 → `폭탄도 나오게` → 폭탄 충돌과 목숨만 추가 → `생선은 더 천천히` → 생선 속도만 변경. 고양이·목표 점수·폭탄 규칙이 사라지면 수정 실패로 판정한다.

성능이 낮은 기기에서는 파티클·그림자·장식 프레임을 낮추되 게임 규칙·속도·충돌은 유지한다. “품질 낮음” 대신 학생에게는 `부드럽게 실행` 설정으로 보여준다.

## 9. 아키텍처 전환 방향

Express·Vercel과 기존 AIroom 경로를 유지한다. 독립 바이브코딩 페이지를 먼저 모듈화하며 메인 교무실 SPA를 전면 재작성하지 않는다. UI 프레임워크 교체를 선행 조건으로 만들지 않는다. 기본안은 ES modules + JSDoc/타입 검사, JSON Schema 계약, 테스트 가능한 순수 로직이다. 타입스크립트를 선택하면 WP0에서 빌드·배포 경로를 한 번에 고정한다.

목표 폴더 및 책임은 병렬 작업 문서에 정의한다. 핵심 경계는 `UI / 프로젝트 상태 / AST·컴파일러 / 게임 실행기 / 서버 AI 정책 / 에셋 작업 / 저장·학생 세션`이다. DOM을 실행기가 직접 수정하지 않고 이벤트·스냅샷으로 UI에 전달한다.

게임 제작은 LLM이 HTML 전체를 작성하게 하지 않는다. 최신 프로젝트와 허용된 도구를 주고 **의도 → 구조화된 변경 → 정적 검증 → 짧은 시뮬레이션 → 브라우저 실행 → 원자적 적용**으로 처리한다. 자세한 예산·계약·복구는 [하네스 문서](./HARNESS-AND-CONTRACTS.md)를 따른다.

## 10. 출시 순서와 규모

기간은 1명 통합 담당 + 독립 작업자 최대 4명 기준의 초기 추정이다. 실제 기기·모델 평가와 기존 코드 분리 난도에 따라 조정하며, 에이전트 수를 늘렸다고 기간을 비례 축소하지 않는다.

| 단계 | 예상 | 산출물 | 통과 게이트 |
|---|---|---|---|
| P0 기반 | 2~3일 | production 기준 확정, 기존 수정 보존, 계약·상태·테스트 틀 | 대표 콘텐츠 동작과 기존 데이터 열기 |
| P1 사용성 | 4~6일 | 큰 단계 UI, 반응형 셸, 카드·도형 편집·채점 | 태블릿/크롬북 실제 미션 수행 |
| P2 게임 신뢰성 | 6~10일 | 3개 기존 장르 고도화, AST 패치, 저장·되돌리기, Groq 평가 | 후속 수정 유지율·실행 성공 기준 |
| P3 운영 | 4~6일 | 미로 템플릿 연결, 에셋 큐, 학급 세션, 교사·사용량 관측 | 30명 부하, 장애·보안·복구 검사 |
| P4 파일럿 | 3~5수업일 | 실제 수업, 실패 관찰, 문구·동선 조정 | 교사 도움 없이 목표 수행, 치명 결함 0 |

일부 작업은 겹칠 수 있으나 계약 확정·통합·사용자 검증은 순차다. 급한 첫 배포는 P0+P1로 잘라낼 수 있고, 이때 “상용 게임 생성 완료”로 표시하지 않는다.

### 우선순위 원칙

P0: 데이터 유실·타 학생 접근·생성물 무검증 적용·작업 불가능한 UI.
P1: 학습 흐름·게임 수정 신뢰성·터치·목표 비교·성능.
P2: 추가 장르·대규모 에셋 확장·꾸밈 효과·공개 갤러리.

세부 승인 기준과 회귀 시나리오는 [검수 문서](./ACCEPTANCE-AND-EVALS.md)에 있다. 기능별 `완료`는 코드 작성이 아니라 증거가 첨부된 게이트 통과를 뜻한다.

## 11. 조사 근거 및 미확정 사항

공식 기술 자료:

- [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs): 모델별 구조화 출력 지원 차이와 현재 스트리밍/도구 호출 제약. 스키마 적합성과 게임 의미 정확성은 별도 검증.
- [Groq Rate Limits](https://console.groq.com/docs/rate-limits): 조직 단위 제한과 여러 종류의 토큰/요청 제한. 실제 조직 할당량은 배포 시 확인.
- [Vercel Functions Limits](https://vercel.com/docs/functions/limitations): 실행 시간·리소스 제약을 확인하고 긴 에셋 작업은 영속 큐로 처리.
- [W3C Target Size Enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html): 터치 타깃 기준 참고.

미확정 사항은 착수를 막지 않는 기본값을 둔다: 동시 한 학급 30명, 2D 게임, 한국어, 학급 내 공유, 기성 에셋으로 즉시 플레이. 실제 Groq 요금제·이미지 공급자·태블릿 OS·학교 관리 정책·최대 동시 학급 수·데이터 보존 기간은 P0에서 환경값으로 확정한다. 학교 정책과 아동 데이터 관련 법적 적합성은 출시 담당자가 별도 검토하며 이 문서는 준법 인증이 아니다.
