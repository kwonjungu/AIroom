# 쭘 파일 변환 확인 (엔진팀 C)

시험일 2026-11-25. 크로미움 145(Playwright), 로컬 정적 서버, 실제 `convert()` 를 메인 스레드에서 호출. 시험 문서는 실제 학교 문서라 저장소에 넣지 않았고 결과 그림도 저장소 밖에 있다. 한/글 프로그램은 쓰지 않았다(원본과의 비교는 쪽 번호 꼬리표와 눈 판정만).

## 3. 0단계 실험 (HWP 세 경로)

같은 HWPX 22쪽/2쪽 문서, 이 PC 크로미움 기준.

| 경로 | 22쪽 | 2쪽 | 결과 |
|---|---|---|---|
| A Worker + OffscreenCanvas measureText + renderPageSvg → 메인 래스터 | 7.3초 | 1.5초 | 그림은 같다. Worker 안에서는 `renderPageToCanvas` 가 OffscreenCanvas 를 못 받아(HTMLCanvasElement 전용) SVG 뿐이다. 글꼴 적재 0.2초 별도 |
| B 메인 `renderPageToCanvas` 한 쪽씩 양보 | 7.6초 | 1.0초 | 통과. 웹폰트가 canvas 에 그대로 쓰임 |
| C 메인 `renderPageSvg` → Image → canvas | 6.1초 | 0.7초 | 속도는 가장 빠르나 SVG 를 Image 로 그릴 때 웹폰트가 안 먹어 글꼴을 SVG 안에 심어야 하고(심으면 9.3초) 다른 브라우저에서 불안 |

시간 차는 세 경로가 서로 20% 안팎이라 결정 요인이 아니다. 쪽 수는 세 경로 모두 같다.

## 4. 고른 경로와 이유

- **HWP·HWPX: B.** 웹폰트(Noto)가 canvas 에 바로 쓰이고, 한 쪽씩 처리해 메모리가 낮고(힙 약 98MB), 취소·시간 제한을 쪽마다 확인할 수 있다. Worker(A)는 어차피 SVG 만 쓸 수 있고, C 는 글꼴 심기가 필요하다.
- **PPTX: @silurus/ooxml 0.90.2(MIT) `PptxPresentation.load` → `renderSlide(canvas, i, {width})`**. 바꾼 이유는 `reports/PPTX_BAKEOFF.md`: PowerPoint 기준 비교에서 가장 가깝고 가장 빠르다. 이전 office-kit 은 웜봇 표지 제목과 글머리 글이 빠졌다.
- **PDF: pdfjs-dist 6.5.438** 본체·worker 해시 고정. 구형 브라우저용으로 `Math.sumPrecise` 를 앞에 붙인다.
- **WASM 배포원:** `rhwp_bg.wasm` 27,882,066바이트, sha256 `e2e56dfd…c9abc1`. jsDelivr 는 `application/wasm`, CORS `*`, br 8.46MB, 0.33초. unpkg 는 같은 헤더, gzip 10.5MB, 2.65초. 1순위 jsDelivr, 2순위 unpkg, 해시가 다르면 다음 주소로 넘어가고 모두 틀리면 HASH_MISMATCH. 글꼴은 Noto Sans/Serif KR(OFL)이며 함초롬체는 재배포 조건이 불확실해 쓰지 않았다.

## 5. 한계

- 글꼴이 Noto 로 바뀌므로 원본과 줄바꿈이 조금 다를 수 있다(`warnings` 에 안내가 들어간다). 중요한 문서는 PDF 로 올리게 안내한다.
- 첫 HWP 변환은 WASM(8~10MB 전송)을 받느라 몇 초 더 걸린다.
- 활동지 설계서(HWP)의 좁은 표는 원본 확인이 필요하다.
- 이 시험은 크로미움 한 종류에서만 했다. 파이어폭스·사파리는 못 돌렸다.

## 6. PPTX 변환기 교체 (office-kit → silurus) 재측정

방법은 이전 비교와 같다. 기준은 PowerPoint 가 뽑은 2000px 그림(bake 폴더), 후보와 500px 로 줄여 RGB 평균 절대 차이(0~1, 낮을수록 가까움). 후보는 이번에는 최종 `convert()` 로 만든 WebP 그림이며 Noto 글꼴을 `fonts` 옵션으로 심은 상태다.

| 문서 | 이전 office-kit | 비교 때 silurus(시스템 글꼴, 원시 호출) | 지금 `convert()`(Noto 심음) |
|---|---|---|---|
| 웜봇 29장 | 0.022 | 0.013 | 평균 0.013, 중앙 0.010, 최대 0.037(29쪽) |
| 바이브 앞 20장 | 0.036 | 0.031 | 평균 0.032, 중앙 0.028, 최대 0.074(16쪽) |

- 글꼴 없는 환경 모의: 웜봇 사본에서 모든 글꼴 이름을 없는 이름(ZZNoFont)으로 바꿔 돌렸더니 한글이 모두 Noto 로 나왔고 평균 0.013, 최대 0.029 로 점수가 같았다. 맑은 고딕 등이 깔린 PC 에서는 그 글꼴이 우선이고, 없는 PC 에서만 Noto 로 바뀐다. 실제 글꼴이 하나도 없는 기기(리눅스 등)에서는 돌리지 못했다.
- 크기: 라이브러리 수십 개 조각을 jsDelivr 에서 받고(압축 전 4.3MB, gzip 1.3MB) WASM 2.03MB 는 별도(br 0.76MB, 0.33~2초). 웜봇 29장 6.2초(첫 실행, 받기 포함), 20장 3.7초. 쪽당 약 50ms 로 SVG 경로(200ms)보다 빠르다.
- 해시: `pptx.mjs` 진입 파일(1197B)과 `pptx_parser_bg.wasm` 은 sha256 확인, 나머지 조각은 버전 고정으로만 막는다. 기본 경로(import map)는 필요 없다. 조각이 진입 파일 기준 상대 경로로 이어지고 WASM 은 `wasmUrl`(검증한 바이트의 blob)로 준다. unpkg 도 같은 해시.
- 기존 경로 확인: HWPX 2쪽, HWP 6쪽, PDF 3쪽, 암호 PDF(PDF_PASSWORD), 큰 그림, PPTX 80장(TOO_MANY_PAGES) 모두 그대로 동작.
- 남은 문제: 16쪽 같은 표 안 글은 줄바꿈이 기준과 달라 점수가 높다. 애니메이션·전환·동영상은 들어가지 않는다. 크로미움 한 종류에서만 시험했다.

## 7. 한도 변경 (60쪽·3분 → 200쪽·6분)

사용자가 쪽 수 한도를 200으로 올렸다(회의 자료는 10일 뒤 지워지는 일시 데이터). `core.js` 의 `maxPages` 200, `maxMs` 6분, 안내 문구 숫자를 맞췄다.

- 바이브코딩 80장 PPTX 전체: 14.0초와 14.9초(두 번), 쪽 그림 합 3.8MB, 썸네일 0.4MB. 쪽 그림은 한 쪽씩 만들어 canvas 를 바로 비우므로 변환이 끝난 시점의 자바스크립트 힙은 약 32MB(Chrome 이 값을 거칠게 줄여 주므로 대략치). 진행 중 최고치는 따로 재지 못했다.
- 65쪽 PDF: 통과, 11.8~12.3초, 3.4MB.
- 200쪽에 가까운 문서에서는 결과 WebP 가 쪽당 약 50KB 로 쌓여 10MB 안팎이며, 시간은 쪽당 0.18초 안팎으로 보면 200쪽에서 40초 안팎이라 6분 안에 들어온다(외삽, 200쪽 실측은 안 함).
- 201쪽 PDF(만든 가짜 문서): TOO_MANY_PAGES 로 거절.
