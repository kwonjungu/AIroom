# 회의 시스템 설계 감사 보고서

감사일: 2026-11-25. 대상: `docs/meeting-2026-11-25/DESIGN.md`. 기준: 같은 폴더의 `AUDIT_BRIEF.md`.

브라우저에서 안건을 이미지로 변환하고 Firestore로 진행 상태를 전달하는 큰 방향은 유지할 수 있다. 다만 공개 시연 경로의 인증 우회, 비공개 투표의 원자료 노출, 인증 없는 대안은 구현 전에 반드시 바로잡아야 한다. **치명 3건, 중요 22건**을 아래에 기록했다. 이 판정은 현 설계를 그대로 구현하거나 운영에 배포해도 된다는 뜻이 아니다.

검토 방법은 설계·저장소 코드의 정적 대조와 공식 기술 문서·업스트림 소스 확인이다. 회의 기능 구현물, Firebase 운영 규칙·결제 콘솔, 실제 학교 문서, 대상 기기의 변환 실행 결과는 확인하지 않았다. 따라서 아래 공격 경로는 설계 및 기존 코드로부터 도출한 것이며 운영 환경에서 공격을 실행한 결과가 아니다. 확인하지 못한 조건은 **추정** 또는 **미확인**으로 표시했다. JEV는 실행 환경을 점검했으나 키 미설정으로 판단에 사용하지 않았다. 학생 자료는 외부로 보내지 않았다.

## 지적 사항

### 01. 공개 `/copy` 경유로 운영 회의 API의 관리자 검사를 통과할 수 있음

- **심각도:** 치명
- **설계 위치:** A-4, B-1·B-2, 구현 단계 1·7
- **문제:** 기존 서버는 `/api/copy/*`를 `/api/*`로 재작성하고, 해당 요청의 `validateSession()`은 토큰 없이도 `COPY_SESSION` 관리자 세션을 반환한다. `COPY_BLOCKED`에는 meetings가 없다. 설계대로 일반 `requireAuth`·`requireAdmin`과 원본 Redis/Firebase를 주입하면, 예를 들어 비로그인 `POST /api/copy/meetings`가 운영 회의를 만들 수 있다. 목록 조회·삭제·토큰 발급에도 같은 경로가 열린다. Redis 키만 분리해도 Firebase 프로젝트·문서·Storage 경로가 같으면 충분하지 않다. **추정:** 새 라우트에 별도 차단 없이 현재 인증 함수를 재사용할 때 발생한다. 아직 회의 라우트는 없다.
- **고칠 방법:** 1차 구현은 `/copy`에서 회의 기능을 제외한다. 재작성 후 `COPY_BLOCKED`에 `/^\/api\/meetings(?:\/|$)/`를 추가하고, 토큰 발급을 포함한 회의 라우터에도 `req.isCopy` 거절을 둔다. 시연을 나중에 지원하려면 Firebase까지 별도 환경으로 분리한다. 비로그인 `/api/copy/meetings`, 생성·삭제·join·host·purge가 모두 거절되고 운영 저장소 호출이 0회인지 검증한다.
- **근거:** `server.js:69`의 `validateSession`, `server.js:94`·`:105`의 인증 미들웨어, `server.js:210` 부근의 URL 재작성, `server.js:230`의 `COPY_BLOCKED`, `server.js:442`의 `COPY_SESSION`; `CLAUDE.md` 「시연용 카피본」.

### 02. 추측 불가 링크 대안은 주관 권한과 로그인 요구를 충족하지 않음

- **심각도:** 치명
- **설계 위치:** B-2 대안, 마지막 결정 필요 1
- **문제:** 회의 ID의 난수성과 `list` 차단은 로그인이나 쓰기 권한 검사가 아니다. 링크를 받은 참석자는 ID를 이미 알고 있다. 진행 권한을 화면에서만 막으면 직접 요청으로 안건·진행·투표를 변조할 수 있다. 요구사항의 “백암이 로그인으로 입장” 및 주관 코드의 의미가 사라진다.
- **고칠 방법:** 인증 없는 대안을 운영 선택지에서 제거한다. 서비스 계정 구성이 불가능하면 서버가 모든 데이터 접근을 인증·인가하는 별도 대안을 설계하거나 기능 공개를 보류한다. 링크 난수는 보조 수단으로만 사용한다.
- **근거:** `AUDIT_BRIEF.md` 맥락; DESIGN A-1·A-2 및 B-2 대안 자체의 “진행 권한은 화면에서만”이라는 설명.

### 03. 비공개 투표와 결과 숨김이 원자료 접근에서 무력화됨

- **심각도:** 치명
- **설계 위치:** B-2 `ballots` 규칙, F-2
- **문제:** 모든 회의 참석자에게 모든 `ballots/{cid}` 읽기를 허용하고 각 화면이 직접 집계한다. 화면에 숫자를 숨겨도 SDK로 전체 표를 읽을 수 있다. `cid`를 `people/{cid}.name`과 연결하면 비공개 표도 이름에 연결된다. 이 문제는 “공식 의결용이 아님”이라는 안내로 해결되지 않는다.
- **고칠 방법:** 원표는 본인의 단건 조회와 제한된 집계 주체만 허용하고 참석자의 전체 목록 조회는 거절한다. 서버 트랜잭션으로 표 변경·이전 선택지 차감·새 선택지 증가·투표 마감 검사를 함께 처리한다. 공개 가능한 집계 문서를 원표와 분리하고, `resultsVisible`일 때만 참석자에게 읽기를 허용한다. 주관자도 개인별 표를 볼 수 있는지 명시한다. 주관자에게도 익명이어야 한다면 원표 읽기를 주관자에게 주지 않는다.
- **근거:** DESIGN B-2의 무조건적인 같은 회의 `allow read`, F-2의 클라이언트 집계·비공개·결과 숨김 조합. 별도 실행 없이 규칙과 요구가 직접 모순된다.

### 04. 맞춤 토큰만으로 주관 권한 12시간·회수·로그아웃이 구현되지 않음

- **심각도:** 중요
- **설계 위치:** A-2·A-3, B-2, G `api.js`
- **문제:** 맞춤 토큰의 교환 유효기간과 로그인 뒤 Firebase 세션 수명은 다르다. Firebase에 로그인한 후에는 세션이 갱신될 수 있다. claims에 `mid/role/cid`만 있으면 12시간 만료, 주관 코드 변경 시 기존 권한 회수, 백암이 세션 만료·로그아웃과의 연동이 없다. `people.role`을 낮추는 것만으로 토큰의 host 권한은 없어지지 않는다.
- **고칠 방법:** 서버가 발급·검증하는 회의 권한 레코드에 세션 식별자, 만료 시각, 권한 버전을 둔다. Rules에서 서버가 정한 만료와 현재 권한을 검증하며 클라이언트는 이 레코드를 수정하지 못하게 한다. 코드 변경 시 기존 주관 권한을 회수할지 명시하고 버전을 올린다. 재발급은 유효한 백암이 세션과 주관 자격을 다시 확인한다. 로컬 Firebase 로그아웃만으로 탈취된 토큰까지 회수된다고 간주하지 않는다. Storage 쪽 실현 방법은 08번과 함께 확정한다.
- **근거:** DESIGN의 12시간 약속과 B-2 claims; `server.js:29` 부근의 기존 백암이 24시간 세션; [Firebase 맞춤 토큰 문서](https://firebase.google.com/docs/auth/admin/create-custom-tokens).

### 05. Firebase UID·기기 식별 결합과 여러 탭의 인증 격리가 빠짐

- **심각도:** 중요
- **설계 위치:** A-2·A-4, B-2, D-3, I
- **문제:** `createCustomToken(uid, claims)`의 UID 생성·보관 방식이 없다. 요청자가 보낸 `clientId`를 그대로 서명한다면 알려진 다른 참석자의 CID를 선택해 표·접속 상태를 대신 쓸 수 있다. **추정:** 발급 서버가 CID를 검증 없이 받는 경우다. 또한 Firebase 기본 local 인증 지속성은 같은 origin의 탭에 동기화된다. 한 탭에서 다른 회의의 `mid`나 viewer 토큰으로 로그인하면 기존 주관 탭의 인증 상태에도 영향을 준다. 같은 브라우저 창 세 개는 독립 참석자 세 명과 같지 않다.
- **고칠 방법:** 서버가 난수 참가 자격을 발급하고 비밀 재접속 자격과 묶어 검증한다. 공유 학교 세션만으로 개인 실명 인증을 보장한다고 표현하지 않는다. 기기별 1표는 “발급된 참가 자격당 1표, 재발급·저장소 초기화로 우회 가능”이라는 한계를 명시한다. 회의용 Firebase 앱 이름과 `session` 또는 `inMemory` 지속성을 정하고 같은 브라우저의 복수 회의를 시험한다. E2E는 독립 BrowserContext를 사용한다.
- **근거:** DESIGN B-2·D-3·F-2; `public/lib/codocs.js:180`의 별도 앱 이름 `codocs`; [Firebase 인증 지속성](https://firebase.google.com/docs/auth/web/auth-state-persistence).

### 06. Rules가 소유자·필드·데이터 크기를 검증하지 않고 역할표와도 어긋남

- **심각도:** 중요
- **설계 위치:** A-1·A-4, B-2, E, F
- **문제:** 참석자는 자기 `people` 문서에 임의 `role/name/handAt`을 쓸 수 있고, `strokes.create`에는 `cid == token.cid` 조건조차 없어 다른 사람 명의의 선을 만들 수 있다. 표의 선택지가 유효한지, 좌표·점 개수·문자열 크기가 제한되는지도 검사하지 않는다. host는 회의 루트 전체를 갱신할 수 있어 관리자 전용 제목 수정과 임의 상태 역행도 가능하다. 다만 `people.role='host'`만 바꿔 토큰 기반 host 검사까지 통과하는 것은 아니다.
- **고칠 방법:** create/update/delete를 나누고 필수·허용 필드, 타입, 길이, 소유자 불변, 서버시각, 안건·쪽 존재, 선택지 ID를 검증한다. `people.role`은 서버 관리 정보로 분리하고 권한 판단에 사용자 입력 이름·역할을 쓰지 않는다. host가 변경할 필드를 `diff().affectedKeys()`로 제한하거나 관리용 메타데이터를 별도 문서로 분리한다. Rules만으로 모든 좌표 원소를 충분히 검증하기 어렵다면 제한된 데이터 표현 또는 검증 API를 사용한다. Storage에도 경로·MIME·파일 크기·개수 정책을 둔다.
- **근거:** DESIGN B-2에 제시된 규칙 전체, C-1의 클라이언트 상한, A-4의 관리자 전용 PATCH.

### 07. 회의 종료와 삭제가 쓰기 권한에 반영되지 않음

- **심각도:** 중요
- **설계 위치:** B-2, D-4, E·F, H
- **문제:** `strokes.create/delete`, `people.write`, `polls.write`는 회의 상태를 확인하지 않는다. ballots도 투표 상태만 확인하므로 회의가 ended여도 투표 문서가 open이면 쓸 수 있다. 부모 회의를 삭제해도 같은 mid의 토큰으로 하위 `people/strokes`를 새로 만들 수 있다. 화면 잠금만 구현하면 오프라인 대기 쓰기도 재연결 때 서버에 들어갈 수 있다.
- **고칠 방법:** 서버 관리 상태의 존재·삭제 중 여부를 모든 하위 쓰기에서 검사한다. 안건 준비는 ready, 주석·손들기·투표는 live, ended는 읽기 전용이라는 허용표를 명시한다. 종료는 서버가 상태를 확정하고 투표 마감도 처리하며, 공통 상태 조건으로 그 사이의 투표 쓰기를 막는다. 종료·삭제 후 지연 쓰기가 거절되어야 한다. 다시 열기가 필요하면 별도 관리자 작업으로 정의한다.
- **근거:** DESIGN B-2 규칙과 D-4의 잠금 약속; [Firestore 부모 삭제와 하위 컬렉션](https://firebase.google.com/docs/firestore/manage-data/delete-data).

### 08. Storage의 실제 다운로드 경로·즉시 회수 방법이 정해지지 않음

- **심각도:** 중요
- **설계 위치:** B-1·B-2, G `viewer.js`, H
- **문제:** “그 회의 토큰으로 읽기”만으로는 파일 표시 경로가 완성되지 않는다. 기존 SPA는 `getDownloadURL()` 패턴을 쓴다. 이를 복제해 공유 가능한 다운로드 URL을 남기면 매번 현재 Firebase 인증을 검사하는 접근 모델과 달라진다. 또한 Storage Rules가 Firestore 문서를 참조해 회수·종료를 확인하도록 고치려 해도, 공식 문서는 다중 DB에서 **기본 DB만 참조 가능**하다고 명시한다. 회의 DB인 `kwon`을 그대로 조회하는 설계는 성립하지 않는다.
- **고칠 방법:** 일반 열람은 인증된 `getBlob/getBytes`와 object URL, 필요한 CORS 설정을 사용하고 영구 다운로드 URL을 문서에 보관하지 않는다. 엄격한 회수는 `(default)`의 별도 접근 제어 문서 또는 서버 인증 게이트 등 지원되는 구조를 선택한다. 짧은 만료 claims/서명 URL로 제한된 회수 지연을 허용할 경우 그 시간을 명시하고 시험한다. 원본도 같은 정책을 적용한다. 이미 사용자가 내려받은 파일·메모리 캐시는 원격 회수할 수 없다는 범위를 구분한다.
- **근거:** `public/index.html:2398`·`:7635`의 `getDownloadURL`; [Storage 다운로드와 SDK 직접 다운로드](https://firebase.google.com/docs/storage/web/download-files), [Storage Rules의 기본 DB 제한](https://firebase.google.com/docs/storage/security/rules-conditions).

### 09. 기존 규칙에 “덧붙이기”만으로 안전한 배포를 보장할 수 없음

- **심각도:** 중요
- **설계 위치:** B-2, 구현 단계 2·8
- **문제:** 저장소에는 `firestore.rules`가 있지만 `storage.rules`는 없고, 운영 Storage 규칙은 확인되지 않았다. 기존에 광범위한 허용 규칙이 있으면 더 좁은 meetings 규칙을 추가해도 권한을 취소하는 효과가 없다. 반대로 전체를 인증 필수로 교체하면 인증 없이 사용하는 기존 codocs·급식 기능이 중단된다. `kwon`과 `(default)`에 잘못 게시하는 위험도 있다. codocs의 규칙 도움말은 `main/firestore.rules`를 가져와 전체 붙여넣기를 안내한다.
- **고칠 방법:** 구현 전에 운영 Firestore·Storage의 현행 규칙을 확보해 전체 합성본으로 검토한다. meetings에 겹치는 넓은 allow를 제거하되 기존 컬렉션 경계를 보존한다. 클라이언트와 Admin SDK 모두 `kwon`을 명시하고, Emulator에서도 그 DB의 규칙이 실제로 적용되는지 확인한다. 전체 규칙 버전·게시 대상·롤백본을 기록하고 codocs 도움말에서 구버전 전체 규칙을 다시 게시해 회의를 막는 상황도 예방한다. Preview의 데이터·버킷·키는 운영과 분리한다.

### 13. 두 주관자의 진행 경쟁과 재연결 시 과거 상태 덮어쓰기를 막지 못함

### 14. 강제 따라가기의 재실행 조건과 화면 좌표 계약이 모호함

### 19. CDN 제한의 적용 범위와 WASM·웹폰트 배포 계약이 불명확함

- **심각도:** 중요
- **설계 위치:** C-2·C-3, B-2 Storage 설명
- **문제:** jsDelivr 공식 제한은 패키지 150MB, GitHub 경로의 단일 파일 20MB로 설명돼 있다. npm WASM 파일에 “파일당 20MB”를 일괄 적용해 배제할 근거는 부족하다. unpkg 우선이라는 것만으로 학교 네트워크 접근·버전 일치·캐시·MIME가 보장되지 않는다. Storage 대안인 `vendor/`는 meetings 전용 규칙 밖이다. 함초롬 웹폰트의 실제 제공 파일·URL·재배포 조건도 없다.
- **고칠 방법:** 실제 0.9.1 JS/WASM 쌍의 URL·바이트 수·해시·Content-Type·CORS·cold/warm 로딩을 측정해 배포원을 결정한다. **27.9MB는 설계 기재값이며 이번 감사에서 바이너리를 내려받아 검증하지 않았다.** vendor 파일은 운영자만 갱신하고 필요한 클라이언트만 또는 공개 정적 자산으로 읽도록 별도 정책을 둔다. 폰트 파일·라이선스·굵기·대체 규칙을 확정하고 로드 실패를 조용히 무시하지 않는다. PDF.js 본체와 worker도 같은 정확한 버전으로 고정한다.
- **근거:** [jsDelivr 공식 제한](https://www.jsdelivr.com/documentation), DESIGN C-3, `package.json:31`의 `pdfjs-dist ^5.6.205`. **미확인:** 실제 CDN 응답과 폰트 재배포 허용 여부.

### 20. 50MB·60쪽 제한만으로 변환 메모리와 확대 가독성을 보장하지 못함

- **심각도:** 중요
- **설계 위치:** C-1·C-3, G-4, H
- **문제:** 압축 파일 크기는 해제된 이미지·문서 모델 크기의 상한이 아니다. 1600×2263 쪽의 RGBA만 약 14.5MB이므로 60장을 동시에 디코딩하면 약 869MB다. 여기에 WASM·원본·압축 해제·썸네일이 더해진다. `pages:[blob...]` 자체가 곧 이 메모리를 차지한다는 뜻은 아니지만, 모든 미리보기를 원해상도로 동시에 디코딩하면 위험하다. 작은 표 글자는 1600px 이미지 확대만으로 복원되지 않는다.
- **고칠 방법:** 페이지 순차 처리와 작은 썸네일 생성, 이미지·canvas·object URL의 명시적 해제, 버퍼 전송, 동시 변환 1개, ZIP 해제 바이트·개별 이미지 픽셀·총 처리 시간 상한을 둔다. 취소 즉시 Worker를 정리한다. 60쪽·50MB 경계와 압축률 높은 손상 파일을 최저 사양 태블릿에서 측정한다. 글자 가독성 합격 기준을 두고 필요하면 고해상도 쪽을 선택 생성하되 용량 추정을 함께 바꾼다.
- **근거:** DESIGN C-1·G-4. 메모리 수치는 `1600×2263×4×60`의 단순 계산이며 **추정**이다. 실제 피크 메모리·변환 시간은 미측정이다.

### 21. `.ppt` 자동 변환 제외는 원 요구와의 합의가 필요한 범위 축소임

- **근거:** `AUDIT_BRIEF.md` 맥락과 DESIGN 0·C-2의 직접 대조. **미확인:** 사용자가 말한 PPT의 확장자 범위.

### 22. 비용 추정에서 구독자별 읽기·원본·요금제 전제가 빠짐

- **심각도:** 중요
- **설계 위치:** D-1·D-3, H
- **문제:** 쓰기 3,000회만으로 무료 한도를 판단할 수 없다. heartbeat 1,800회를 30명이 전부 구독하면 읽기 약 54,000회, 진행 갱신 300회를 30명이 받으면 약 9,000회다. 초기 조회·주석·투표·재연결·Rules 의존 문서 읽기는 별도다. 300ms마다 계속 쓰는 최악의 1시간은 진행 쓰기 약 12,000회다. Storage 8MB는 쪽 그림만의 추정으로 원본 최대 4×50MB, 썸네일, WASM·폰트, 재다운로드가 빠졌다.
- **고칠 방법:** 구독 문서×갱신 횟수×구독자 수로 통상/최대 시나리오를 계산한다. 접속 명단은 주관자만 구독하고 참석자 수는 느린 집계로 주는 등 읽기를 줄인다. 기본 이미지 40쪽×30명은 캐시 없는 최초 로딩 약 1,200개 객체 요청이다. 원본은 요청할 때만 받고 현재·다음 쪽 중심 캐시를 둔다. Vercel API 호출, Upstash 명령, Storage 객체 작업·전송, 보관 중 누적 회의까지 따로 산정하고 측정·예산 알림 기준을 둔다.
- **근거:** [Firestore 구독 과금](https://firebase.google.com/docs/firestore/pricing), [Storage 요금제 변경](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024). 위 계산은 **추정**이며 실제 전원 people 구독 여부에 따라 달라진다. 2026-02-03부터 Storage 사용에는 Blaze가 요구된다. 실제 프로젝트의 결제 상태·버킷 리전은 **미확인**이다. 무료 DB에 대해서도 현재 Firebase 문서는 “이름과 관계없이 첫 생성 DB”, Google Cloud 문서는 “named DB는 무료 제외”라고 설명이 달라 `kwon`의 무료 적용을 단정하지 않는다. [Google Cloud 가격 문서](https://cloud.google.com/firestore/pricing)와 실제 Billing에서 확인해야 한다.

### 23. 보관 만료·전체 삭제를 한 번의 Cron 성공에 의존함

- **심각도:** 중요
- **설계 위치:** A-4 DELETE·purge, H, 구현 단계 7
- **문제:** 부모 Firestore 문서를 삭제해도 하위 컬렉션은 자동 삭제되지 않는다. Storage·Redis까지 한 요청에서 삭제하면 timeout·부분 실패·중복 실행에 취약하다. 종료되지 않은 ready/live 회의와 실패 업로드의 보관 기한도 없다. 만료 판정을 Cron에만 맡기면 30일이 지난 뒤에도 다음 실행까지 열람된다. Vercel Cron은 Preview에서 자동 실행되지 않고 실패 시 자동 재시도하지 않는다.
- **고칠 방법:** `endedAt/purgeAfter`를 기준 저장소에 두고 만료 시 접근 차단과 물리 삭제 완료를 구분한다. 먼저 `deleting` 상태·권한 회수로 새 쓰기를 막고, 재개 가능한 작은 묶음으로 Storage·모든 하위 컬렉션·원표·캐시를 삭제한다. 작업 ID·cursor·잠금·재시도·마지막 성공 시각을 보존하고 완료 후 목록을 제거한다. 준비만 한 회의·고아 업로드 정책도 정한다. 일일 Cron은 놓친 기간 전체를 처리하고 GET+Bearer 검증, 비밀키 미설정 거절, UTC 일정, 실행시간 상한을 명시한다.
- **근거:** [Firestore 삭제 문서](https://firebase.google.com/docs/firestore/manage-data/delete-data), [Vercel Cron 운영 조건](https://vercel.com/docs/cron-jobs/manage-cron-jobs), `vercel.json`의 기존 채용 Cron. 참고로 `lib/recruitment/routes.js:118`은 POST purge만 등록한다. 회의의 GET 계획은 맞으며, 기존 채용 구현을 그대로 복제하면 메서드 불일치를 물려받을 수 있다. 기존 채용 문제의 수정은 이번 감사 범위 밖이다.

### 24. 관리자 입장·두 SPA·미러·기존 배포 지침과의 통합 계약이 빠짐

- **심각도:** 중요
- **설계 위치:** A-1·A-4, G, 구현 단계 7·8
- **문제:** A-1은 관리자에게 안건·진행 권한을 주지만 `/join`은 viewer, `/host`는 주관 코드가 있어야 host다. 관리자 우회 경로가 없다. 새 독립 페이지를 두 벌 만들 필요는 없지만 메인 바로가기 카드는 루트와 public SPA 모두에 반영해야 한다. - **근거:** `CLAUDE.md` 「두 SPA」·「rewrite」·「학교 공간」·「배포」; `server.js:316`의 public 정적 서빙, `lib/hub/index.js`의 독립 세션; DESIGN A-1과 A-4.

## 더 단순한 구현 대안

요구를 유지하면서 복잡도를 줄이려면 회의 메타데이터·안건·진행 상태는 Firestore 한 곳을 기준으로 하고 Redis는 코드·로그인 잠금 등 비밀 정보에 한정하는 편이 낫다. 주관자는 여러 명이어도 **진행자는 한 번에 한 명**으로 정한다. 투표 쓰기·집계는 작은 서버 API로 모으고, 참석자에게는 공개된 집계만 전달한다. `/copy`와 `/hub` 확장은 첫 구현에서 제외한다.

Storage의 즉시 권한 회수가 꼭 필요하면 회의용 제어 데이터를 `(default)` DB에 두는 대안도 비교할 수 있다. 기존 codocs의 `kwon`은 유지할 수 있지만 새 DB의 비용·전체 Rules·백업 설정을 별도로 검증해야 한다. 이 선택 없이 `kwon`을 Storage Rules에서 직접 읽는 방법을 전제해서는 안 된다.

PDF·이미지만 먼저 운영하는 방안은 구현이 더 단순하지만 한/글·PPT 자동 변환 요구를 줄이는 선택이다. 사용자가 범위 축소를 받아들인 경우에만 단계 출시 대안으로 삼고, 현재 요구를 충족한 것으로 표시하지 않는다.

## 구현 전에 확정할 사항

기존 세 가지 결정에 더해, 구형 `.ppt` 범위, 관리자 host 발급 경로, 권한 회수의 최대 지연, 비공개 투표에서 주관자의 원표 접근 여부, 단일 진행권 인계, 미종료 회의·고아 파일 보관 정책, Firebase 결제·DB·Storage 규칙 배치를 확정해야 한다. **01~03번 치명 사항과 04~12번의 권한·데이터 일관성 계약을 먼저 수정한 뒤** 기능 구현을 진행하는 것이 타당하다. 변환기는 17~20번의 최소 실험을 통과한 경로만 채택한다.
