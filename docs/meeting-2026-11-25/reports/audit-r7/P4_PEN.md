## 1. 꼭 찾을 것: 「지우개로 지우면 다른 기기에서 25초 지나도 안 사라짐」

### 1-1. 서버가 쓰는 것
- `DELETE /:mid/strokes/:sid` (routes.js:948~966): `guarded()` 트랜잭션 안에서 `tx.get(strokes/sid)`, 주인 확인, 그다음 **`tx.delete(sub(mid,'strokes',sid))`** (routes.js:959). 표시를 남기는 방식도 아니고 epoch 를 올리지도 않는다. **Firestore 문서를 실제로 지운다.**
- gcp.js:151~171 `runTransaction` 은 모아 둔 쓰기를 `:commit` 으로 보낸다(`{delete: name}`, gcp.js:107). ABORTED 이면 다시 한다. 200 이 돌아왔다면 커밋까지 끝난 상태다(커밋이 실패하면 throw 해서 200 이 나갈 수 없다).

## 2. 그 밖의 발견

### P4-1 (보통) epoch 짐작 선이 epoch 구독이 늦게 오면 말없이 사라짐
- 위치: draw.js:379~383(4초 뒤 epoch=0, guessed), draw.js:354~359 `dropStale`.
- 무엇이 틀렸나: `dropStale` 은 `p.epoch < en.epoch && status !== 'sending'` 이면 pending 에서 뺀다. 짐작으로 0 을 넣은 선도 똑같이 뺀다. 그런데 짐작한 선을 진짜 값으로 고치는 길은 서버 stale_epoch 응답(430~431) 하나뿐이다.
- 재현: 주관자가 한 번 「모두 지우기」를 해서 epoch=1 인 쪽에서, 학교망이 멈춰 epoch 구독이 늦는다. 참석자가 선을 긋고 4초가 지나면 epoch=0 으로 짐작한다. POST 가 연결 실패(429·0)로 백오프에 들어가 `queued` 가 된다. 연결이 돌아오며 epoch 스냅숏(1)이 먼저 오면 `dropStale` 이 그 선을 지운다. **토스트도 없이 내 화면에서 선이 사라지고 저장도 안 된다.**
- 고칠 방향: `dropStale` 에서 `p.guessed` 인 선은 버리지 말고 `p.epoch = en.epoch; guessed=false` 로 고쳐 다시 보낸다.

### P4-2 (보통) 사람당 300획은 지운 획도 세는데, 안내는 「내 선을 지우라」고 함
- 위치: routes.js:919 메시지, routes.js:962~964(`who=''` 로 되돌림), keys.js:136(`who ~= ''` 일 때만 사람 몫을 줄임).
- 무엇이 틀렸나: 사람 몫은 쓴 선 수라 지워도 돌려주지 않는다(주석에 적힌 의도). 하지만 409 메시지는 「내 선을 지우거나 주관자에게 쪽 지우기를 부탁하세요」라고 한다. 지워도 풀리지 않는다. 1,500점을 넘는 긴 선은 조각마다 1로 센다.
- 재현: 주관자가 화이트보드 한 쪽에서 쓰고 지우기를 되풀이한다(한글 글자 1자에 2~5획이니 80자 안팎). 300획이 차면 새 선마다 저장이 안 되고 선이 사라진다(draw.js:447~450, remove). 안내대로 지워도 계속 막힌다. 주관자 본인도 같은 한도를 받는다. 쪽 지우기를 하면 모두의 선이 사라진다.
- 고칠 방향: 메시지를 「이 쪽에 쓸 수 있는 선을 다 썼어요. 새 쪽(화이트보드 쪽 추가)을 쓰거나 주관자가 쪽을 지워야 해요」로 바꾼다. 또는 지울 때 사람 몫도 돌려주고(`who` 를 넘김), 도배 방지는 초당 한도에 맡긴다. 주관자를 한도에서 빼는 것도 생각해 볼 만하다.

  - 1280: 쪽 [256,150,666,500] 이니 아래 끝 y=650, 오른쪽 끝 x=922. 펜 단추 (780,619) 139×44. 펜을 끈 상태에서도 쪽 오른쪽 아래 139×31px 이 가려진다.

### P4-4 (보통) 휴대폰에서 펜 선이 약 1.5px, 빠르게 그으면 약 0.75px
- 위치: draw.js:11(`pen.w 0.004`), draw.js:59(`size = w × pageW`, 최솟값 0.5 는 쪽 px 기준이라 화면에서는 뜻이 없음).
- 무엇이 틀렸나: 선 굵기는 화면에 보이는 쪽 너비 × 0.004 다. 390 폭에서 쪽 너비 372px 이면 1.49px 이다. 손가락과 마우스는 `simulatePressure` 이고 thinning 이 0.5 라서 빠르게 그은 구간은 반쯤 더 가늘어진다(약 0.75px). PC(쪽 666px, 2.7px)에서 쓴 글씨도 휴대폰에서는 1.5px 로 보인다.
- 재현: 휴대폰 세로로 쪽 전체 보기를 하고 펜(검정)으로 글씨를 쓴다. 획이 머리카락처럼 가늘어 회의실 화면 공유나 작은 화면에서 읽기 어렵다.
- 고칠 방향: 그릴 때 화면 기준 최솟값을 둔다(`size = max(w*pageW, 2.2/vp.scale)`). 또는 pen.w 를 0.006 으로 올린다(서버 범위 0.001~0.05 안).

### P4-5 (보통) 따라가기·확대 중에 긋는 선이 엉뚱한 자리에 저장됨
- 위치: draw.js:543(획을 시작할 때 `vp:{...vp}` 고정), 521(점을 고정 vp 로 바꿈), 298(temp 도 고정 vp 로 그림). viewer.js:523~528(같은 쪽에서 발표자가 확대·이동하면 `glideTo` 로 따라 움직임).
- 무엇이 틀렸나: 따라가기 중인 참석자가 펜으로 긋는 동안 발표자가 확대하거나 옮기면, 무대와 ink 는 새 화면으로 움직인다. 그런데 그리는 획은 옛 배율로 쪽 좌표를 계산한다. 손가락 아래 내용과 저장되는 자리가 어긋나고, 그리는 중인 선도 자료에서 떨어져 보인다. 펜 모드에서 ctrl+휠로 확대해도 같다. 발표자가 쪽을 넘기면 `setPage` 에서 `cancelDrawing()`(draw.js:337) 이 불려 긋던 획이 말없이 버려진다.
- 재현: 발표자가 같은 쪽에서 확대해 옮기는(live 120ms 묶음) 동안 참석자가 휴대폰 펜으로 밑줄을 긋는다. 손을 떼면 밑줄이 확대 전 자리 기준의 다른 위치에 저장되어 모두의 화면에 나타난다.
- 고칠 방향: 획을 그리는 동안(`drawing` 이 있을 때)은 viewer 가 live 반영을 미뤘다가 손을 뗀 뒤 적용한다(store 'drawing' 신호). 또는 점마다 지금 vp 로 바꾼다.

### P4-6 (낮음) SEND_GAP 350ms 와 서버 초당 3회
- 위치: draw.js:30, 395~398, 412. routes.js:54, 898. 서버 한도는 고정 창(1초 경계, routes.js:149)이다.
- 판단: 클라이언트는 한 번에 하나만 보낸다(`sending`). 다음 보내기는 앞 응답이 온 뒤, 앞 보내기를 시작한 때에서 350ms 가 지난 뒤다. 서버 처리(Redis 여러 번과 Firestore 트랜잭션: begin, get 3종, commit)와 한국에서 iad1 까지 왕복을 더하면 도착 간격은 사실상 350ms 보다 길다. 한 창에 4번 들어갈 일은 드물다. 실측(SEND_GAP 1050 시절) POST 간격도 1.5~1.9초로 왕복 시간이 묶음을 정했다. 429 가 와도 백오프(1, 2, 4초) 뒤 같은 묶음을 최대 20개까지 다시 보내고, 6번 실패해야 흐려지며 「다시 보내기」가 나온다. 데이터 손실 경로는 없다.
- 남는 점: 0.35초로 줄여도 체감 지연은 왕복 시간이 정한다. 지연 줄이기 A 의 효과는 확인 못 함(바뀐 뒤 운영 실측 기록이 없다). DELETE 는 판서 한도가 아니라 일반 8회 통(`pt()` 기본, 'all')을 POST 와 함께 쓴다. 쓰고 지우기를 동시에 몰아 하면 POST 약 2.9 + DELETE 약 3.8 = 6.7회/초로 여유가 적다. DELETE 가 429 를 받으면 다시 보내지 않고 선을 되살리며 오류 토스트를 띄운다(draw.js:481~486). 주석의 「서버 초당 5회 한도」(draw.js:31)는 서버에 없는 값이다.
- 고칠 방향: DELETE 도 429·0 이면 백오프 뒤 다시 보낸다. 여러 개를 지울 때는 묶음 지우기 라우트를 만든다.

### P4-7 (낮음) 보내는 중에 지운 내 선이 지운 사람 화면에 잠깐 다시 나타남
- 위치: draw.js:506~508, 420.
- 무엇이 틀렸나: `sending` 상태에서 지우면 `p.erased` 만 켜진다. 저장이 성공하면 `enqueueDelete` 를 부르지만 `cur.hidden` 에는 넣지 않는다. 지우기 요청이 닿기 전에 구독이 그 문서를 가져오면, pending 이 빠지고(328) 서버 선으로 다시 그려진다. 지우기가 커밋된 뒤 사라진다.
- 고칠 방향: 420 에서 `cur.hidden.add(x.id)` 도 함께 한다.

### P4-8 (낮음) stale_epoch 로 진짜 epoch 를 알아도 같은 쪽의 다른 epoch 모름 선은 다시 4초를 기다림
- 위치: draw.js:435. `en.epoch` 만 바꾸고 `resolveEpoch(en)` 와 `schedule()` 을 부르지 않는다. 지연만 생긴다.

### P4-9 (낮음) 펜을 한 번 쓰면 그 뒤로 손가락으로는 못 그림
- 위치: draw.js:242, 528~529. `penSeen` 은 새로고침 전까지 풀리지 않는다. 패드에서 펜을 쓰다 내려놓고 손가락으로 그리면 아무 반응도 안내도 없다.

## 3. 점검했지만 문제 없던 것
- epoch 짐작 경로의 서버 쪽: 짐작 0 < 진짜 epoch 면 scReserve 는 그 쌍을 예약하지 않는다(keys.js:66). 트랜잭션은 `stale_epoch` 를 `extra:{pageKey,epoch}` 와 함께 돌려주고(routes.js:937), api.js:93~95 가 extra 를 넘겨준다. 그러면 draw.js:430~431 이 진짜 값으로 다시 보낸다. 예약 되돌리기도 epoch 가 달라 아무것도 하지 않는다. 문제 없다(단 P4-1 은 남음).
- 쪽당 2,000, 회의당 2만: 지우면 `scRelease` 로 돌려준다(쪽 몫). 쪽 지우기는 `scDrop` 이 옛 epoch 사람 몫까지 지운다(keys.js:146~161).
- 남의 선 지우기: 화면에서도 거르고(draw.js:497) 서버에서도 막는다(routes.js:958, not_owner).
- 묶음 20개 한도: 클라이언트(406~409)와 서버(896)가 같다. 조각 21개 한도와 겹친 점 이어 붙이기(splitPts, mergeGroups)도 맞다.
