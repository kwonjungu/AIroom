## 2. 찾은 문제

### N1. [보통] 따라가는 중에 「쪽 전체 보기」나 키 0 을 누르면 발표자 배율로 되돌아간다 (P3-3 덜 고쳐짐)
- 위치: viewer.js:448-452 (fitPage). setTarget(411)·setView(454)·onDown(652)에는 cancelGlide 가 들어갔지만 fitPage 에는 없다. fitPage 는 `S.view` 를 직접 바꾸므로 진행 중인 glideTo 의 다음 프레임이 그 값을 다시 덮는다.
- 재현(실측 S2·S2b): 따라가는 중에 발표자가 z=3 에서 z=1.5 로 바꿨다. 20ms 뒤 「쪽 전체 보기」(또는 키 0)를 눌렀다. 최종 page.view 는 `{z:1.5}` 였고 follow 는 free 로 바뀌었다. 쪽 맞춤(z=1)이 되지 않고, 따라가기도 풀렸다.
- 영향: 발표자가 확대해 설명하는 회의에서 「쪽 전체 보기」를 누르면 가끔 안 먹고, 자유 보기로만 빠진다.
- 고칠 방향: fitPage 맨 앞에서 cancelGlide() 를 부른다.

### N2. [보통] 휴대폰 펜 최소 굵기 2.2px 가 실제로는 적용되지 않는다 (P4-4 안 고쳐짐)
- 위치: draw.js:59-60. `size = max(2.2, w × pageW)` 에서 pageW 는 화면 너비가 아니라 **쪽 원래 px**(vp.pageW = viewer geo().pageW)이다. PDF 는 긴 변 2000px(convert/core.js:8), 화이트보드는 1600px(viewer.js:5)이다. 그리기는 applyViewport(draw.js:115)가 vp.scale 로 줄인다.
- 실측(node 로 strokeOptions 호출):

| 자료 | 쪽 px 기준 size | 휴대폰(쪽 372px) 화면 굵기 |
|---|---|---|
| A4 세로 PDF(1414) | 5.66 | 1.49px |
| 가로 슬라이드(2000) | 8.00 | 1.49px |
| 화이트보드(1600) | 6.40 | 1.49px |

  w × pageW 가 늘 2.2 보다 크므로 최솟값은 한 번도 쓰이지 않는다. 휴대폰 펜은 여전히 1.49px 이고, 빠르게 그은 곳은 thinning 0.5 때문에 그 반쯤으로 가늘어진다.
- 그래서 과제에서 물은 영향(지우개 판정, 형광펜, PC 화면)은 **지금은 없다.** 형광펜은 `tool==='hl'` 이면 0.5 로 따로 두었고, 지우개 hitStroke(draw.js:164)는 굵기를 쓰지 않는다(반경 12px 고정). PC 는 원래 2.66px 이라 바뀌지 않는다.
- 고칠 방향: R7 제안대로 화면 기준으로 건다. `size = max(w·pageW, 2.2 / vp.scale)`. 이때 경로 캐시 열쇠(draw.js:96 `@pageWxpageH`)에 배율 구간을 넣어야 확대·축소 때 옛 굵기가 남지 않는다. 고친 뒤에는 휴대폰 화면에서 픽셀로 굵기를 재서 확인한다.

### N3. [보통] 「이 자료 발표하기」가 「오늘의 안건 펼치기」와 같은 자리에 겹칠 수 있다 (새 위치의 경쟁 상태)
- 위치: viewer.js:1064 (`ui:wait` 를 받을 때만 is-below-mini 를 붙임), agenda.js:152 (모양이 **바뀔 때만** `ui:wait` 를 냄), app.js:118-132 (모듈을 Promise.all 로 동시에 불러 먼저 받은 것부터 붙임).
- 무엇이 틀렸나: viewer.js 는 약 56KB, agenda.js 는 약 26KB 다. 학교망에서는 agenda.js 가 먼저 붙어 첫 render 에서 `ui:wait 'mini'` 를 내기 쉽다. 그 뒤에 붙은 viewer 는 이 알림을 놓친다. 그러면 큰 단추가 is-below-mini 없이 `top: var(--zz-s3)` 에 놓여 za-mini(같은 left·top, 같은 min-width 196px·높이 48px, 같은 z-index 6)와 겹친다. #zz-wait 가 DOM 뒤쪽에 있어 안건 단추가 위에 오므로 「이 자료 발표하기」가 통째로 가려진다.
- 재현(실측 S4): viewer 를 붙이기 전에 `ui:wait 'mini'` 를 냈다. 큰 단추는 hidden=false, class 에 is-below-mini 가 없었고, 무대 위에서 top 12px(za-mini 와 같은 자리)였다. 붙인 뒤에 같은 알림을 다시 내면 is-below-mini 가 붙었다.
- 언제 보이나: 진행 중인 회의에 들어온 참석자는 안건 모양이 바로 mini 가 된다. 이 사람이 자유 보기로 가거나 발표자가 발표를 끝내면(live.aid 없음, 이때는 안건이 full 로 바뀌었다가 닫힘) 단추가 나타난다. 「지금 보는 자료를 바로 발표」가 안 보이는 셈이다. 쪽 막대의 「오늘의 안건 보기」 단추 판단(waitShown, viewer.js:913)도 같은 원인으로 어긋난다(예전부터 있던 문제).
- 고칠 방향: viewer 가 붙을 때 지금 모양을 읽는다. 예를 들어 agenda.js 가 `store.set('waitMode', mode)` 로 값을 남기고 viewer 가 시작할 때 `store.get` 한다. 아니면 CSS 로 `#zz-wait.is-mini ~ …` 같은 DOM 기준 배치를 쓴다.

### N4. [보통] 발표 화면 보내기가 멈추는 시간은 여전히 최대 약 19초다 (P3-5 덜 고쳐짐)
- 위치: api.js:401 (`timeout: 6000`), api.js:77·81·105-107 (POST 는 시간 초과도 catch 로 가서 3번까지 다시 보냄, 사이 0.3초·1초), viewer.js:577 (`P.inflight` 동안 새 화면은 dirty 만 세움).
- 무엇이 틀렸나: 시간 초과로 abort 되면 request() 의 catch 가 이를 연결 실패로 보고 같은 몸통(같은 idem)을 다시 보낸다. 그래서 6 + 0.3 + 6 + 1 + 6 ≈ 19.3초 동안 inflight 가 풀리지 않는다. 그동안 발표자가 넘긴 쪽은 참석자에게 가지 않는다. live 는 마지막 값만 뜻이 있는데, 옛 몸통을 세 번 다시 보내는 셈이다. 같은 idem 에 서버가 `in_progress` 를 주면 1.5초씩 더 기다린다(api.js:88-90).
- 재현(코드 근거): 학교망에서 /live 요청 하나가 응답 없이 멈추면, 발표자 화면은 3쪽인데 참석자는 약 19초 동안 1쪽에 머문다. 실제 멈춤 빈도는 확인 못 함.
- 고칠 방향: sendLive 는 request 의 다시 보내기를 끈다(예: `tries: 1` 옵션). 실패하면 flushLive 가 그때의 최신 view 로 새로 보낸다. 3번 실패한 뒤에도(viewer.js:609-611) P.dirty 를 남겨 두고 조금 뒤 다시 보낸다.

### N5. [낮음] PC 에서 펜 모드일 때 확대한 쪽을 옮기기 어려워졌다 (P3-6 고침의 부작용)
- 위치: viewer.css:188 (`body.is-pen .zv-sb { pointer-events: none }`), viewer.js:731 (휠은 늘 확대·축소만), 667-671 (펜 모드에서 옮기기는 두 손가락이나 마우스 가운데 단추만).
- 무엇이 틀렸나: 예전에는 펜 모드에서도 스크롤 막대를 끌어 옮길 수 있었다. 이제 막대가 누름을 통과시키므로, 가운데 단추가 없는 노트북 터치패드나 교실 PC 마우스로는 확대한 쪽을 옮길 방법이 없다. 두 손가락 스크롤도 휠 이벤트라 확대·축소가 된다. 펜을 꺼야만 옮길 수 있다.
- 고칠 방향: 막대에서 마우스(pointerType 'mouse')만 받고 펜·손가락은 통과시킨다. CSS 로는 못 가르므로 막대 pointerdown 에서 펜·터치이면 아래 캔버스로 넘기는 식으로 JS 에서 가른다.

### N6. [낮음] 미끄러지는 중 무대를 한 번 누르면, 「따라가는 중」인데 화면이 중간 배율에서 멈춘다 (cancelGlide 위치의 새 회귀)
- 위치: viewer.js:652. onDown 이 단추 거르기 바로 뒤, 펜 모드 판단보다 **앞에서** cancelGlide() 를 부른다. 움직이지 않는 탭, 펜 모드의 한 손가락·펜·마우스 긋기 시작은 userChanged 를 부르지 않는다. 그래서 follow 는 'follow' 그대로이고, 끝까지 가지 못한 view 가 남는다. glideTo 가 끝날 때 하던 `S.view = to` 와 emitPage 도 일어나지 않는다.
- 재현(실측):
  - S3: 따라가는 중 발표자가 z=1 에서 z=3 으로 바꾸고 40ms 뒤 무대를 한 번 클릭했다. 결과는 page.view z=2.468, follow 'follow', live z=3.
  - S3b: 펜 모드에서 펜 pointerdown 을 냈다. 결과는 z=2.175, follow 'follow'.
- 영향: 띠에는 「발표 화면을 보고 있어요」라고 나오는데, 발표자보다 덜 확대된 화면에서 멈춘다. 발표자가 확대한 뒤 그대로 설명하면 다음 live 가 올 때까지 이어진다. 펜 모드에서 참석자가 발표자의 확대를 따라가며 쓰는 상황이 가장 잘 겹친다. 0.14초 창이라 자주 일어나지는 않는다.
- 고칠 방향: onDown 에서는 실제로 옮기기·확대를 시작할 때(startPan·startPinch, 그리고 setView)만 멈춘다. 아니면 멈출 때 `S.follow==='follow'` 이면 목표 view 로 바로 맞춘다(cancelGlide(snap)).

### N7. [낮음] 이미 저장된 짐작 선은 쪽 지우기 뒤에도 그 기기 화면에 남는다 (dropStale guessed 처리의 새 회귀)
- 위치: draw.js:360. 조건이 `p.guessed && p.status !== 'sending'` 이라 'saved' 상태도 들어간다. guessed 는 저장에 성공해도 지워지지 않는다(draw.js:416-419).
- 재현(코드 근거): epoch 0 인 쪽에서 실시간 연결이 멈춘 참석자가 선을 긋는다. 4초 뒤 0 으로 짐작해 저장에 성공한다(saved, guessed). 구독이 오기 전에 주관자가 쪽 지우기(epoch 1)를 한다. 연결이 돌아와 epoch 1 이 오면 dropStale 은 이 선을 버리지 않고 epoch 를 1 로 바꾼다. 서버에서 그 선은 epoch 0 이라 구독(현재 epoch 만)에 다시 오지 않는다. 그래서 pending 에서 빠지지 않고, paintInk(draw.js:285-288)가 계속 그린다. 그 기기에서만, 새로 고칠 때까지 지운 쪽에 선이 남는다. 다른 기기에서는 사라져 있다.
- 비슷한 경우: 'queued' 짐작 선을 그린 뒤에 쪽 지우기가 일어났다면 그 선은 지우기 뒤에 새 epoch 로 저장되어 다시 나타난다. 짐작한 선은 그린 때를 가를 수 없으니 드문 손실과 드문 부활 가운데 무엇을 고를지 정해야 한다.
- 고칠 방향: 바꾸기 대상을 `(status==='queued' || status==='failed') && parts 에 id 가 하나도 없음` 으로 좁힌다. 저장에 성공하면 `p.guessed = false` 로 둔다.

### N8. [보통, 시험 결함] 운영 점검의 지우개 판정은 선이 처음부터 안 왔어도 「사라짐」으로 나온다
- 위치: tests/zzoom/prod_pen_check.py:303-304 (둘째 기기에 나타났는지 dt 를 적기만 하고 확인하지 않음), 313-316 (`cover < 0.2` 면 사라짐).
- 무엇이 틀렸나:
  1. dt 가 None(25초 안에 안 나타남)이어도 지우개 시험을 그대로 한다. 그러면 cover 는 처음부터 0 이라 곧바로 「사라짐 0.x초」로 적힌다. 「지운 선이 다른 기기에 남는다」를 가려내려고 만든 시험이 거꾸로 거짓 통과를 낸다.
  2. 지우기 전 둘째 기기의 cover 를 기준값으로 재지 않는다. r=3 은 촘촘하다(±1·±3 격자). 휴대폰 화면 굵기는 1.49px 이다(N2). 둘째 기기 좌표는 쪽 크기 비율로 바꾼 값(conv)이고, streamline 0.5 로 선이 입력점보다 뒤로 밀린다. 이것들을 합치면 지우기 전에도 cover 가 0.2 아래일 수 있다. 실제 값은 확인 못 함(운영에서 다시 재지 못함).
  3. bandp1(310)은 이제 쓰지 않는 변수다.
- 고칠 방향: 지우기 전에 둘째 기기 cover 를 재서 0.8 이상일 때만 지우개 판정을 한다. 판정은 「지우기 전 대비 0.2배 미만」으로 한다. dt 가 None 이면 「판정 불가」로 적는다.

## 3. 확인했고 문제없던 것
- **onDown 단추 거르기**: 무대 안 조작 요소는 덮개의 큰 단추, 오류 덮개의 「다시 불러오기」, 스크롤 막대뿐이다. `button, a, input, .zv-sb` 로 모두 걸러진다. 펜 모드에서는 막대가 pointer-events none 이라 누름이 펜 캔버스로 바로 간다. 무대 손짓(빈 곳 끌기·두 손가락)은 그대로였다(S7 휠, R7 v2 시나리오).
- **cancelGlide 를 setTarget 에 넣은 것**: applyLive 의 쪽이 바뀌는 경로도 setTarget 을 거치지만, 이 경로는 원래 tween 을 멈추던 곳이라 동작이 같다. 안건이 바뀌어 setTarget 을 부르는 경로(viewer.js:1028·1034)는 follow 일 때 applyLive 를 다시 부르므로 목표값으로 맞춰진다.
- **keepAsk**: stale_rev 메아리 뒤 force 를 되살려 0ms 로 다시 보내도 되풀이 고리는 없다. sendLive 가 409 의 live 로 acceptLive 해 baseRev 가 새로 맞춰진다(api.js:405). 사용자가 그사이 전체 화면을 다시 누른 경우 새 값(`P.fullWant !== undefined`)이 이긴다.
- **큰 발표 단추 숨김 조건**: /presenter/end 는 live.aid 를 null 로 만든다(routes.js:586). 그래서 발표자가 없을 때 `othersOn` 이 참으로 남아 단추가 영영 숨는 일은 없다(S1: 발표자 없음이면 보임). 내가 발표자이고 다른 자료를 볼 때도 보인다. 전체 화면(`!on`)과 펜 모드에서는 숨는다.
- **is-below-mini 위치 계산**: za-mini 는 min-height 48px, 한 줄 글이라 `s3 + 48 + s2` 로 맞다(viewer 가 알림을 받았을 때).
- **P3-2·P3-6 CSS**: `body.is-pen` 은 app.js:306 이 실제로 붙인다.
- **R7 v3.py 재실행**: 실패 뒤 다시 보낸 요청에 full·force 가 실렸다. live 묶음 간격은 최소 139.6ms(14건)로 서버 한도 10/s 안이다.

## 4. 고치지 않은 R7 낮음 항목(참고)
FIXES 의 「고치지 않은 것」에 P4-6~9(DELETE 재시도 없음, 보내는 중 지운 선이 잠깐 다시 보임, stale_epoch 뒤 resolveEpoch 를 안 부름, penSeen)와 1-4(획 POST 재전송 중복 문서)는 적혀 있지 않지만 코드는 그대로다. 1-4 는 이번 X-Zzoom-Idem 으로 request() 안의 재전송은 막혔다. draw.js 의 백오프 재전송(saveStrokes 를 새로 부름, 새 idem)은 여전히 같은 선을 두 문서로 만들 수 있다. 모두 낮음이라 다시 지적하지 않는다.
