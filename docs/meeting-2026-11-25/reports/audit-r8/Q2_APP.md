## 2. 고치면서 새로 생긴 문제

### 보통

#### N1. 회의 시작·끝내기·판서 잠금·녹음 상태 보내기가 학교망 「곧바로 실패」에 더는 다시 보내지 않음(회귀)
- 파일:줄: public/zzoom/api.js:92(`if (a < tries - 1 && !keepalive)`), api.js:384(setState 는 늘 `keepalive: true`), host.js:111·125·226, record.js:304·416
- 무엇이 바뀌었나: 고치기 전에는 3초 안에 실패한 보내기(학교망 실측 ERR_ADDRESS_UNREACHABLE·핸드셰이크 끊김)를 keepalive 여부와 상관없이 다시 보냈다. 지금은 keepalive 면 한 번도 다시 보내지 않는다. setState 는 탭을 닫을 때만이 아니라 평소 「회의 시작하기」「회의 끝내기」「판서 잠그기」「녹음 켜기」에도 keepalive 로 간다.
- 재현: 학교 와이파이가 잠깐 끊긴 순간 「회의 시작하기」를 누른다. 예전엔 0.3초 뒤 다시 보내 성공했는데, 지금은 곧바로 「서버에 연결하지 못했어요」가 뜬다. 녹음 켜기(record.js:304)도 같아 녹음이 시작되지 않는다.
- 고칠 방향: keepalive 는 탭을 닫는 경로(record.js:404)에서만 쓰게 setState 에 옵션을 두거나, 다시 보내기 금지를 `document.visibilityState === 'hidden'` 일 때로만 좁힌다(같은 요청 표가 있으니 다시 보내도 안전하다).

#### N2. 주관자 전환 중 「나가기」를 눌러도 실시간 로그인 실패 뒤 회의로 되살아남
- 파일:줄: api.js:296-311(becomeHost catch), 232-238(begin 실패 경로), 323-327(leave)
- 무엇이 틀렸나: catch 는 `e.code === 'aborted'` 만 거른다. 실시간 로그인(fbSignIn)은 8초씩 4번, 길게는 40초 가까이 걸리는데 그사이 사용자가 회의에서 나가면 `gen` 이 올라가도 begin 은 aborted 가 아니라 firebase_auth 오류를 던진다. catch 가 그 오류를 받아 S 를 새로 세우고 하트비트를 켜고 `sset('role', host)` 를 한다.
- 재현: 메뉴, 「회의 담당자로 들어가기」, 맞는 번호를 누른 뒤 실시간 로그인이 멈춘 동안 회의 목록으로 돌아간다. 몇십 초 뒤 실패가 확정되면 목록에 있는데 role 이 다시 서고 하트비트가 1분마다 나가며(접속자 명단에 남음), onRole 이 회의 화면을 다시 붙인다.
- 고칠 방향: catch 맨 앞에서 `if (myGen !== gen) throw aborted();` 를 먼저 본다.

#### N3. 12초 「처리 중」 넘겨받기와 20초 시간 제한이 맞물려, 12초 넘게 걸리는 보내기는 다시 보낼 때 서버가 같은 일을 한 번 더 함(커밋 전 변경)
- 파일:줄: lib/zzoom/routes.js 같은 요청 표 미들웨어(작업 폴더 125-137줄, `staleMs` 12000·70000·40000), api.js:63(기본 20초)·81-93
- 무엇이 틀렸나: 화면은 20초 시간 초과 뒤 같은 표로 다시 보낸다. 그때 서버 표시는 이미 20초가 지나 12초 기준을 넘었으므로 서버는 앞 요청이 아직 돌고 있어도 새로 처리한다. 즉 서버 처리가 12초를 넘는 보내기에는 같은 요청 표의 보호가 없다. DELETE 는 기준 40초인데 화면 시간 제한이 45초라 같은 모양이다.
- 경로별 결과:
  - 회의 지우기: 45초 시간 초과, 곧바로 두 번째 DELETE 처리. 사람당·접속지·전체 지우기 상한(10·20·40)을 한 번 더 깎고 정리를 한 번 더 돈다. 정리는 멱등이라 데이터 손상은 없다.
  - 회의 만들기(routes.js:328): 회의 목록을 읽는 시간이 12초를 넘으면 같은 회의가 두 개 생길 수 있다. 실제로 12초를 넘는지는 확인 못 함.
  - 업로드 확정(자료 바꾸기): 744475c 에서 응답 전에 쪽 epoch 거래(쪽마다 차례로 읽기, 최대 200쪽), 쪽마다 Lua 한 번, 옛 선 지우기 8초, 옛 그림 지우기 8초가 더해져 20초를 넘길 수 있다. 두 번째 확정은 `a.base === upBase` 로 이미 끝난 것으로 보고 정리 없이 답하므로 결과는 맞다(낮은 영향).
- 고칠 방향: 「처리 중」 기준을 그 경로의 화면 시간 제한보다 길게 둔다(기본 25초, DELETE 50초, 받아쓰기 70초 유지). 또는 앞 요청이 살아 있는지를 시각 대신 갱신되는 표시로 본다. 자료 바꾸기 뒷정리는 응답 뒤 정리 예약(purgePages)에 맡겨 확정 응답을 빨리 준다.

#### N4. 발표 화면 보내기(/live)가 다시 여러 번 보내져 P3-5(멈춘 요청이 발표 화면을 막음)가 도로 생김
- 파일:줄: api.js:398-399(sendLive timeout 6000), api.js:80-94(보내기 3번, in_progress 기다리기), viewer.js:577·585(한 번에 하나만 보냄)
- 무엇이 틀렸나: 시간 제한을 6초로 줄였지만, 744475c 부터 시간 초과도 다시 보내므로 한 번의 sendLive 가 6초+0.3초+6초+1초+6초, 약 19초 동안 끝나지 않는다. 그동안 viewer.js 는 `P.inflight` 라 새 화면을 보내지 못하고, 다시 보내는 몸체는 처음 잡아 둔 **옛 쪽·옛 확대값**이다. viewer.js 는 실패 시 자기 재시도(800ms×횟수, 최신 화면으로)를 따로 갖고 있어 api 단계 재시도가 필요 없다. 두 번째 시도가 in_progress 를 받으면 서버 12초 기준까지 1.5초마다 더 기다린다.
- 재현: 발표자 패드 연결이 몇 초 멈춘다. 그사이 쪽을 세 번 넘겨도 참석자 화면은 약 19초 동안 그대로이다가, 옛 쪽이 한 번 나온 뒤에야 최신 쪽으로 간다.
- 고칠 방향: request 에 `retry: false` 옵션을 두어 /live(그리고 같은 이유로 /heartbeat)는 한 번만 보내고, 다시 보내기는 viewer.js 가 최신 몸체로 하게 한다.

## 3. 확인했고 문제없던 것
- scheduleRefresh 재시도와 permission-denied 즉시 갱신이 겹쳐도 `clearTimeout(S.timers.refresh)` 로 타이머는 하나만 남는다. 동시에 refresh 가 두 번 돌아도 로그인은 authOp 줄로 차례대로이고, 두 토큰 모두 1시간 유효라 어느 쪽이 나중에 앉아도 괜찮다.
- 업로드 출입증과의 꼬임: refresh 는 응답을 받은 **뒤** `uploading` 을 보므로, 업로드 시작 전에 줄에 선 보통 로그인은 업로드 로그인보다 먼저, 업로드 중 받은 토큰은 pending 으로 간다. 업로드가 끝나면 pending 또는 새 refresh 로 돌아간다.
- 강등 뒤 people 구독은 onRole 이 바로 끊어 권한 거절 반복 갱신이 생기지 않는다(전환 사이 한 번 정도 더 갱신될 뿐).
- 같은 요청 표 키에 pt(또는 로그인 토큰)가 들어가 다른 사람이 같은 표로 남의 응답을 받을 수 없다. 기억한 응답에 맞춤 토큰이 들어가지만 2분 뒤 사라지고 키를 알려면 표와 pt 를 다 알아야 한다.
- 응답을 res.json 밖(res.send)으로 주는 경로는 GET export.md 뿐이라 표 저장이 빠지는 보내기 경로는 없다. res.json 뒤에 다시 throw 하는 경로도 찾지 못했다.
- `request` 의 `timedOut` 변수는 이제 쓰이지 않는다(동작 영향 없음).
- agenda.css `.za-mini` min-width 196px: 360px 에서 왼쪽 12px+196px 로 넘치지 않는다.
