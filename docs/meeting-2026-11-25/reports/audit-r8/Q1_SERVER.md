## 찾은 문제

### Q1-1 높음: 운영 Redis(Upstash)에서는 저장해 둔 처음 응답이 절대 다시 나오지 않는다. 같은 표로 다시 보내면 언제나 409 in_progress 다
- 위치: routes.js(744475c) 127-130. 작업 폴더 128-135(`raw[0] === '{'`, `raw[0] === 'p'`). server.js 414 `new Redis({ url, token })`(automaticDeserialization 기본값 true)
- 무엇이 틀렸나: 미들웨어는 결과를 `JSON.stringify({s,b})` 문자열로 적고, 읽을 때 문자열이라고 가정한다. 그런데 @upstash/redis 는 `get` 에서 JSON 으로 읽히는 값을 **객체로 바꿔** 돌려준다. 그래서 커밋본에서는 `JSON.parse(객체)` 가 예외를 내고 `prev=null` 이 된다. 작업 폴더본에서는 `raw[0]` 이 undefined 라 `prev=null`, `since=0` 이 된다. 둘 다 같은 표는 120초 동안 409 in_progress 를 받는다. 작업 폴더의 「12초 뒤 넘겨받기」도 `since=0` 이라 동작하지 않는다. 시험용 가짜 Redis(fake-redis.js:23)는 문자열을 그대로 돌려줘서 api.test.js 의 두 시험이 이 차이를 잡지 못한다. 같은 저장소의 다른 코드는 `U.parseJson`(문자열과 객체를 모두 받음)으로 이 함정을 피하고 있다.
- 재현(스크립트로 확인)
  - upstash-get.js: `set(k, '{"s":201,...}')` 다음 `get(k)` 는 `object {"s":201,"b":{...}}` 이고, 미들웨어 판정은 「409 in_progress」다.
  - idem-repro.js, Upstash 처럼 바꾼 get, 커밋본과 작업 폴더본 둘 다 결과가 같다.
    1. 참석자가 `/host`(주관 코드)를 보내 200 을 받는다. 서버는 이때 옛 pt 를 지웠다.
    2. 같은 표로 다시 보내면 **409 in_progress** 다. 61초 뒤에 보내도 409 다.
    3. 옛 pt 로 채팅하면 401 pt_invalid 다.
  - 가짜 Redis 에서는 2단계가 200 이다.
- 실제 상황: 학교망에서 `/host` 응답이 끊기면 api.js request 가 같은 표로 다시 보낸다. 409 를 1.5초 간격으로 5번 받은 뒤 오류를 낸다. becomeHost 는 새 pt 를 받지 못한다. 서버는 옛 pt 를 이미 지웠으므로 다음 요청이 401 pt_invalid 가 되고, onGrantError 가 자격을 지워 회의에서 쫓겨난다. R7 P5-M1 이 고치려던 바로 그 장면이다. 채팅, 안건, 투표도 반영은 됐는데 화면에는 「앞서 보낸 같은 요청을 처리하는 중입니다」 오류가 뜬다. 그래서 사용자가 다시 누르면(새 표) 결국 두 번 올라간다. 진행자가 말한 「운영에서 in_progress 가 23초 이어졌다」는 Vercel 얼림만이 아니라 이 원인으로도 설명된다(23초 ≈ 1.5초×5회 + 시간 제한).
- 고칠 방향: 읽은 값을 `U.parseJson(raw)` 로 다룬다(객체면 그대로). 처리 중 표시는 `typeof raw === 'string' && raw[0] === 'p'` 로 가린다. 또는 이 키만 `automaticDeserialization:false` 클라이언트로 읽는다. 가짜 Redis 에도 Upstash 처럼 get 이 JSON 을 해석하는 선택을 넣어 시험이 잡게 한다.

### Q1-2 보통(작업 폴더본): 처리 중 넘겨받기 12초가 화면 제한(20초)보다 짧아, 느린 요청은 다시 보내면 두 번 처리된다
- 위치: 작업 폴더 routes.js 125(`staleMs` 12초, DELETE 40초, 받아쓰기 70초) 와 136(넘겨받기 SET 에 NX 가 없음). api.js 63 `REQ_TIMEOUT_MS = 20000`
- 무엇이 틀렸나: 화면은 20초가 지나 끊기면 같은 표로 다시 보낸다. 서버의 앞 요청이 12초보다 오래 걸리며 아직 도는 중이면 뒤 요청이 「죽은 요청」으로 보고 새로 처리한다. 같은 표가 막으려던 경우는 바로 「서버가 느려서 응답이 늦은」 경우인데, 이때 두 번 반영된다. 넘겨받기는 NX 없이 덮어써서, 다시 보낸 요청 두 개가 겹치면 둘 다 처리할 수 있다. (Q1-1 을 고치면 이 경로가 실제로 쓰이게 된다.)
- 재현(코드 읽기로 확인): Firestore 충돌 재시도(gcp.js runTransaction 최대 5번)나 Q1-3 의 자료 바꾸기처럼 15초 걸린 요청이 있다. 화면이 20초에 끊고 다시 보낸다. 뒤 요청이 넘겨받아 다시 처리한다. 업로드 확정(commit)은 안에서 `already` 로 막히지만 채팅, 안건 만들기, 투표 열기, 화이트보드 만들기는 하나 더 생긴다.
- 고칠 방향: 넘겨받는 시간을 그 요청의 화면 제한보다 길게 잡는다(기본 25초 이상, DELETE 50초, 받아쓰기 70초). 넘겨받기는 그 'p<시각>' 값일 때만 바꾸는 원자 연산(Lua 비교 후 바꾸기)으로 한다.

### Q1-3 보통: 자료 바꾸기 뒷정리가 응답 앞에서 수십 초까지 길어질 수 있고, 쪽 epoch 트랜잭션이 실패하면 옛 선이 하나도 지워지지 않는다(이전보다 나빠짐)
- 위치: routes.js(작업 폴더) 800-820(744475c 는 780-801)
- 무엇이 틀렸나
  1. 트랜잭션 하나에서 옛 쪽 수만큼(최대 200) `tx.get` 을 **하나씩 차례로** 부른다(gcp.js get 은 매번 REST 왕복). 이어서 scDrop 을 쪽마다 차례로 부르고, removeOldStrokes 를 최대 8초, removePrefix 를 최대 8초 돈다. 모두 끝나야 201 을 보낸다. 바꾸기 전에도 Storage 목록 확인과 WebP 머리 확인을 이미 한다. 그래서 큰 PDF 를 바꾸면 화면 제한 20초를 넘기기 쉽다. 커밋본에서는 Q1-1 때문에 성공했는데도 오류로 보인다. 작업 폴더본에서는 12초 넘겨받기로 commit 이 `already:true` 를 받아 성공으로 보인다.
  2. 200개 쪽 문서를 읽어 잠근 채 오래 머무른다. 그 쪽들에 저장하는 판서 트랜잭션과 부딪히면 ABORTED 가 되고, 5번 넘게 부딪히면 예외가 난다. 예외는 `catch → console.warn` 으로 삼키므로, 쪽 epoch, 장부, purgePages, 옛 그림 지우기(removePrefix 도 같은 try 안)가 **모두 건너뛰어진다**. 예전 코드는 적어도 옛 선 500개를 바로 지웠다. 이제는 하나도 안 지워지고 옛 선이 새 자료 위에 그대로 보인다. R7 P1-3 의 증상이 이 경로에서 다시 나온다.
  3. 바꾸기 트랜잭션(안건 자료 교체)과 쪽 epoch 트랜잭션 사이에 새 자료 위에 그린 선은 옛 epoch 로 저장된다. 곧 epoch 가 올라가면 말없이 사라진다(틈은 수 초).
- 재현(코드 읽기로 확인): 150쪽 PDF 안건에서 참석자 몇 명이 그 안건을 보며 판서하는 중이다. 주인이 「자료 바꾸기」를 한다. 쪽 epoch 트랜잭션이 판서 저장과 부딪혀 5번 실패하면 서버 로그에 「자료 바꾸기 뒷정리 실패」만 남는다. 새 자료에는 옛 선이 보이고, 옛 쪽 그림은 회의를 지울 때까지 Storage 에 남는다. Firestore 위치(왕복 시간)와 Vercel 함수 최대 실행 시간은 **확인 못 함**. 함수가 중간에 끊기면 purgePages 예약도 빠진다.
- 고칠 방향: 쪽 문서는 한 번에 읽는다(Promise.all 또는 batchGet). 또는 epoch 올리기를 바꾸기 트랜잭션 안에 넣는다. purgePages 예약은 트랜잭션 **앞에** 둔다. 옛 선 지우기와 그림 지우기는 각각 따로 try 로 감싸 하나가 실패해도 나머지를 한다. 오래 걸리는 지우기는 응답 뒤가 아니라 정리 작업에 맡기고 곧바로 답한다(쪽 키에 `ver` 를 넣는 방법도 있다).

### Q1-4 낮음(작업 폴더본): 모든 보내기 응답이 Redis 쓰기 한 번만큼 늦어진다
- 위치: 작업 폴더 routes.js 147-149
- 내용: res.json 은 이제 Redis SET 이 끝난 뒤 보낸다. 들어올 때 SET NX 도 하므로 보내기마다 Redis 왕복이 둘씩 차례로 붙는다. 0.35초 간격 판서와 0.12초 묶음 /live(화면 제한 6초)에 그대로 더해진다. res.json 뒤에 응답 머리나 res.end 를 쓰는 라우트는 찾지 못했다. 모든 res.json 은 핸들러 끝에서 부른다(grep 으로 41곳 확인). 그래서 오류 처리기가 두 번 응답하는 경로는 지금은 없다. 다만 앞으로 res.json 뒤에 코드를 두면, 아직 안 보낸 응답의 상태 코드가 바뀌거나 두 번 보내다가 `.then` 안에서 처리되지 않은 예외가 날 수 있다.
- 고칠 방향: /live 와 판서처럼 자주 오고 다시 보내도 문제없는 요청은 같은 표를 빼거나, 결과 저장을 `waitUntil` 로 넘긴다. 그리고 `.then(() => json(body))` 에 catch 를 단다.

### Q1-5 낮음: 전체 회의 지우기 상한(10분 40개)을 한두 사람이 다 써 버릴 수 있다
- 위치: routes.js 385-387
- 내용: 상한 셋은 차례로 센다. 이미 'deleting' 이거나 대기열에 있는 회의를 다시 지워도 센다(`m || queued` 만 확인). 그래서 한 사람이 같은 회의 id 로 DELETE 를 되풀이하거나 두 접속지에서 보내면 전체 40칸이 차고, 10분 동안 관리자를 포함한 모두가 지우지 못한다(429). 학교는 접속지 하나를 같이 쓰므로, 한 교사가 지난 회의 20개를 정리하면 같은 학교의 다른 교사도 10분 막힌다. 관리자 예외가 없는 것(P1-8)은 R7 낮음이라 덧붙이기만 한다.
- 고칠 방향: 이미 'deleting' 인 회의는 상한을 세지 않는다. 전체 상한과 접속지 상한은 관리자에게 걸지 않는다.

### Q1-6 낮음: scReserve 가 더는 장부를 스스로 맞추지 않아, 쪽 지우기와 겹치거나 scDrop 이 실패하면 쪽 개수가 조금 틀어진다
- 위치: keys.js 66-81, routes.js 1026-1029·808
- 내용
  1. 쪽 지우기에서 Firestore epoch 를 E+1 로 올린 뒤 scDrop 이 돌기 전에, 새 epoch(E+1) 저장이 들어오면 그 수가 옛 개수에 더해진다. 곧이어 scDrop 이 그것까지 0 으로 만든다. 그래서 새 선 몇 개가 쪽 개수에서 빠진다(덜 세는 쪽이라 상한이 조금 느슨해질 뿐이다).
  2. scDrop 이 Redis 오류로 실패하면(자료 바꾸기 루프 중간 실패 포함) `@e` 가 옛 값에 남는다. 예전에는 다음 저장이 장부를 새 epoch 로 옮겨 스스로 고쳐졌지만, 이제는 옛 개수가 다음 쪽 지우기 때까지 남아 쪽 상한(2,000)을 일찍 채울 수 있다. 사람당 몫은 epoch 가 키에 들어 있어 영향이 없다.
- 고칠 방향: 지금 그대로 둬도 된다. 다만 1은 쪽 지우기 Firestore 트랜잭션 앞에 scDrop 「예고」를 두거나 scDrop 결과를 다시 확인하면 줄일 수 있다. 2는 실패를 경고로 남기고 purgePages 처럼 다시 해 보도록 예약한다.

### Q1-7 낮음: 같은 요청 표가 로그인 없는 요청에도 Redis 쓰기를 만들고, pt·맞춤 토큰 원문을 Redis 에 2분 동안 둔다
- 위치: routes.js 120-150
- 내용
  1. 미들웨어가 로그인·자격 확인 **앞에** 있다. 그래서 아무나 POST 에 표만 붙이면 요청마다 Redis 쓰기가 2번 생긴다(재현: 로그인 없는 POST 5번에 Redis 호출 10번). 120초 만료라 쌓이지는 않고 비용만 는다.
  2. `/join`·`/host`·`/refresh` 응답에는 pt 원문과 Firebase 맞춤 토큰이 들어 있다. 이 응답이 그대로 `zz:idem:*` 에 2분 동안 저장된다. 「Redis 에는 pt 해시만」이라는 설계 원칙과 어긋난다. Redis 를 읽을 수 있는 사람만 쓸 수 있으므로 낮음이다.
- 다른 사람 응답을 받을 위험: 키는 표, 메서드, 주소, pt(없으면 백암이 세션 토큰)의 해시다. 남의 응답을 받으려면 그 사람의 표와 pt(또는 세션 토큰)를 모두 알아야 하는데, 그렇다면 이미 그 사람 자격을 가진 것이다. pt 와 세션 토큰이 둘 다 없는 보내기는 화면에 없다(sendBeacon 은 표를 못 붙여 미들웨어를 건너뜀). 그래서 다른 사람 응답을 받는 경로는 찾지 못했다. 본문은 키에 없지만 화면은 다시 보낼 때 같은 본문을 쓴다(api.js request).
- 고칠 방향: 미들웨어를 `pt()`/`login` 뒤(라우트별)로 옮기거나, 적어도 X-Zzoom-Pt·X-Auth-Token 이 없으면 건너뛴다. 저장할 때 pt·token 칸은 빼거나 암호화한다.

## 확인했고 문제없는 것
- 업로드·받아쓰기 원본 본문: express.raw 는 받아쓰기 라우트 안(routes.js 1257)에 있다. 미들웨어는 본문을 읽지 않으므로 409 를 먼저 보내도 본문 처리에 문제가 없다. 받아쓰기 주소에는 `?at=` 가 들어가 조각마다 키가 다르다. 받아쓰기는 화면 60초, 서버 45초, 넘겨받기 70초라 서로 어긋나지 않는다.
- 속도 제한과의 순서: 같은 표 응답과 409 는 pt 속도 제한 앞에서 끝나 한도를 쓰지 않는다. 다시 보낸 요청이 한도를 두 번 쓰는 일은 없다. 5xx 와 429 는 저장하지 않고 지워 다시 해 볼 수 있다.
- finish 정리: res.json 을 거치지 않은 응답(경로 없음 404 등)은 finish 에서 키를 지운다.
- 짐작 epoch 0 경로: 장부 `@e`=E>0 일 때 e=0 은 세지도 늘리지도 않는다. stale_epoch 뒤 scRelease 는 `E <= 0` 이 거짓이라 건드리지 않는다. `@e`=0 이고 Firestore 도 0 이면 그대로 맞다. `@e`=0 인데 Firestore epoch 가 더 크면 e=0 예약은 거절 뒤 되돌려진다. 큰 epoch(999999)는 쪽 개수에 더해졌다가 거절 뒤 그대로 빠지고, `@e` 는 움직이지 않는다(api.test.js 새 시험과 같음).
- 선 지우기 scRelease(`''`, e=선의 epoch): 지금 epoch 선만 줄이고, 쪽 지우기로 버린 옛 epoch 선은 건드리지 않는다.
- 자료 바꾸기 쪽 epoch: `tx.set(pages/<키>, {epoch})` 로 통째로 쓰지만 pages 문서에는 epoch 말고 다른 칸이 없다(routes.js 976·1015 와 같은 모양). 쓰기 200개는 Firestore 한 번 커밋 한도(500) 안이다. purgePages 값 형식(`<mid>|<쪽 키>` → epoch)은 쪽 지우기·runPurge 와 같다.
